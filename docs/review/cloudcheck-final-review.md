## 3. 남은 결정 — 기획팀장 결정

### 3-1. F-1(ExternalId 값 미고지): 베타에는 넣지 않는다. v0.1.1의 첫 항목으로 넣는다

- **결정**: AWS-KEY-4 '못 보는 것'에 다섯째 줄을 더하는 일을 띠를 떼기 전 v0.1.1에 넣는다. 첫 push 전에 바이트를 바꾸지 않는다.
  - 문구 초안: `cc.rule.aws-key-4.cannot.5` = "ExternalId 조건에 든 값(* 처럼 아무 값이나 통과시키는 조건인지는 구분하지 못함)"
  - 톤 · 명사구 규칙은 디자인팀장이 확정한다.
- **이유**:
  1. **베타 차단 기준에 해당하지 않는다.** QA 결정 §6 보정 1의 차단 기준은 두 가지다. 정상 경로의 근거 없는 이상 없음, 그리고 범위 · '없음'의 과장이다.
     - F-1의 이상 없음 문장("외부 AWS 계정을 ExternalId 조건 없이 믿는 역할이 없습니다")은 글자 그대로 참이다. 룰이 묻는 것도 조건이 있느냐다.
     - 모자란 것은 '못 보는 것' 목록의 한 줄이다. 거짓 진술이 아니라 고지 누락이다.
  2. **검증이 끝난 바이트를 마지막에 바꾸는 쪽의 위험이 더 크다.** QA · 디자인 실브라우저 재확인과 PM 수동 확인이 모두 c9f68992…를 기준으로 한다. 비차단 항목 때문에 재생성 · 재검증 고리를 다시 도는 것은 마지막 순간의 범위 늘리기다.
  3. **노출이 작다.** 베타는 noindex이고 홍보하지 않는다. 첫 실사용자는 PM이다. 와일드카드 ExternalId는 드문 안티패턴이다[일반 지식]. 외부 테스터는 v0.1.1 뒤에 들인다(§3-4 D-B).
  4. **어차피 v0.1.1이 있다.** CC-QA-01 잔여 알림 때문에 판정을 바꾸지 않는 릴리스가 띠를 떼기 전에 한 번 필요하다. F-1은 거기에 얹는다. 예산은 같은 릴리스의 중복 문구 정리로 상쇄한다(§3-3).
- **함께 정한 것**:
  - v0.1.1에서 카탈로그 문구가 바뀌므로 `RULESET_VERSION`은 1.0.0 → 1.0.1로 올린다.
  - 근본 해결은 수집기가 'StringLike 값에 `*` · `?`가 있는지' 불리언만 투영하는 것이다(계약 minor 추가, 값 자체는 계속 수집하지 않음). 이것은 수집기 묶음(§4-3)으로 한다.

### 3-2. Tailwind 편차: 알려진 편차 G5-TW1로 기록하고 베타에서 받아들인다

- **사실** [보고: 프론트 리뷰 F-1]: 루트 Tailwind가 `src/app/**`를 훑으면서 생성물 · 문구 키에서 쓰이지 않는 규칙 4개(`.collapse` · `.m-16` · `.m-7` · 무효 선언 1개)를 만든다. 867 → 871 규칙, +117 B(압축 전)다. 방향서 G5의 "규칙 수 증가 0"에 문자 그대로는 맞지 않는다.
- **받아들이는 조건**:
  1. 4개 이름을 쓰는 요소가 0이어야 한다.
     - 프론트팀장 측정: HEAD `src/**` · `public/**` [보고]
     - 이번 확인: cloudcheck 밖 추적 파일에 `m-${…}` 같은 동적 조립 · `collapse` 클래스 0 [확인]
  2. 배포 전후로 `/pae` 응답이 가리키는 전역 CSS를 받아 규칙 수를 비교한다. 차이가 **정확히 +4**여야 한다. 더 많으면 원인을 확인하기 전까지 롤백을 검토한다.

### 4-6. 첫 push 이후 규칙

1. **수집기**: 바이트가 바뀌면 `CC_VERSION`을 올리고 `make-release.mjs`로 `RELEASES.json` · `SHA256SUMS`에 **추가**한다. `--reset`은 금지다. 옛 릴리스 항목은 지우지 않는다(옛 결과 파일을 계속 알아보게).
2. **룰셋**: 판정 로직이 바뀌면 `RULESET_VERSION` minor를 올린다. 카탈로그 문구(조건 · 못 보는 것 · 기준값)만 바뀌면 patch를 올린다.
3. **페이지**: PAGE.sha256이 바뀌면 `PAGE_VERSION`을 올린다. 같은 파일 이름(`cloudcheck-<버전>.html`)에 해시가 둘 생기지 않게 한다.
4. **공개된 수집기**: 첫 push부터 `5547c91e…`는 공개 저장소에 실린 것이다. PDF 인쇄 전이라도 바꾸지 않는 것을 기본으로 한다(C-11). 바꿀 때는 §4-3처럼 묶어서 한 번에 한다.
5. **정답지**: 고치면 같은 파일 `notes`에 바뀐 칸과 근거를 남기고 QA가 리뷰한다. 엔진 출력으로 만들거나 갱신하지 않는다(F-3에서 얻은 교훈).
6. **생성물 · 시험**: 생성물은 프론트팀장이나 메인 세션만 재생성한다. 수정과 `it.fails` → `it` 전환은 같은 변경으로 넣는다(레포 전체 `npm run test`가 다른 앱의 배포 게이트다).
7. **공유 파일**: 9종 수정은 0이다. 불가피하면 blast radius를 고지하고 PM 승인을 받는다.
8. **시험 리터럴**: 새 시험에 공급자 형식의 비밀 리터럴을 쓰지 않는다(실행 중에 조립). AWS 문서의 공개 예시만 예외다.
9. **배포**:
   - `git push mingame main`을 쓴다(origin 아님).
   - 경로 한정 커밋을 한다. `git add -A`와 force push는 금지다. 배포는 하나씩 직렬로 한다.
   - 라이브는 200 응답이 아니라 PAGE.sha256과 고유 콘텐츠로 판정한다.
10. **공개 범위**:
    - noindex는 `BETA_NOINDEX`로만 다루고 G9에서 뗀다.
    - Azure는 C 묶음 + Azure V1 뒤에 `CLOUD_AVAILABILITY.azure`로만 연다.
11. **예산**: §3-3.
