## 0. 결론

**만들 수 있다. 다만 어려운 건 게임이 아니라 숨기기다.**

- 실시간 방은 /pae의 `useRoom.ts` 패턴을 거의 그대로 쓴다. 바꿀 것은 세 가지다. 낡은 상태를 거르는 방식(액션 순번 → 서버 버전 번호), 시간 기준(브라우저 시계 → 서버 시각), 화면이 사라질 때 자동으로 나가는 처리 삭제.
- 숨기기는 **한 방향**으로 설계한다. 몇 번을 눌러도 숨기만 하고, 다시 게임으로 돌아가는 건 하단 시트 탭을 클릭할 때뿐이다. 허둥대며 Tab을 두 번 누르면 토글 방식은 게임을 다시 띄우기 때문이다.
- 프론트 일정은 **약 3.5작업일**이다(계약 고정 0.5일, 병렬 개발 2일, 통합·검수 1일). 여기에 예비 0.5일을 둔다. 3일차 통합 전까지 Supabase가 다시 켜져 있어야 한다(G0-1).
- 기획서에서 프론트 관점으로 고칠 곳은 8군데다(§7). 가장 큰 건 두 가지다. ① 두 판을 나란히 둔 화면과 "열 A~H가 곧 좌표"라는 규칙이 하나의 시트 안에서는 같이 성립하지 않는다. ② 도발 문구를 업종 팩에 넣으면 보낸 사람과 받은 사람이 서로 다른 문장을 본다.

## 2. 실시간 방: useRoom.ts에서 가져올 것과 새로 쓸 것

`src/lib/pae/useRoom.ts`는 고치지 않는다. 패턴만 본떠 `src/lib/monthly-close/client/useMcRoom.ts`를 새로 쓴다.

### 2-1. 그대로 가져올 것

1. `getSupabase()`, `ensureAnonUid()` import. 익명 로그인과 세션 유지는 같다.
2. Bearer 토큰을 붙여 POST하는 `api()` 헬퍼.
3. **액션 응답에 담긴 최신 공개 상태를 바로 반영**(다시 조회하는 왕복 없음).
4. 테이블 3개에 postgres_changes 구독 + 신호를 놓칠 때를 대비한 1초 폴링.
5. 주기적인 tick(접속 신호 + 기한 처리), 액션이 거부되면 즉시 다시 동기화.
6. 타이머·채널 정리 패턴.

### 2-2. 바꿀 것

| # | /pae 방식 [확인] | 월마감 방식 | 이유 |
|---|---|---|---|
| 1 | 액션 순번(`actionSeqRef`)으로 낡은 폴링 결과를 버림. 폴링 때마다 매번 setState | 서버가 상태를 바꿀 때마다 올리는 **버전 번호 `ver`**로 비교. 더 새로울 때만 반영하고, 같으면 setState 자체를 안 함 | 순번 방식은 추측이라 빈틈이 있다. 그리고 /pae는 1초마다 화면 전체를 다시 그린다. 월마감은 판 2개 + 위장 시트 300칸이 매초 다시 그려지면 안 된다 |

### 2-3. 새로 쓸 것

1. **view_state 보고**: 숨거나 돌아올 때 즉시 `fetch(..., {keepalive:true})`로 보내고, 매 tick에도 현재 값을 같이 보낸다. 화면 전환은 이 요청을 절대 기다리지 않는다. 기획 A-1의 API 목록에는 이 경로가 없다(§7-8).
2. **개인 데이터 복원**: 내 배 위치, 내가 받은 힌트 값, 퀴즈 오답 잠금 시각은 본인만 읽을 수 있는 행(RLS)에 둔다. 새로고침해도 힌트가 사라지지 않아야 한다.
3. **오류 코드**: 서버는 `STALE`, `NOT_YOUR_TURN`, `ROOM_FULL`, `EXPIRED`, `RATE_LIMITED` 같은 코드를 주고, 화면은 이를 시트 프로그램 말투로 바꾼다("다른 사용자가 먼저 편집했습니다", "문서를 찾을 수 없습니다").
4. **RoomController 인터페이스**: 실시간 방(`useMcRoom`)과 박대리 연습(`usePracticeRoom`)이 같은 모양(상태 + place/fire/answerQuiz/ackQuizShown/useHint/reportAlarm/sendTaunt/reportView/rematch/leave)을 돌려준다. 그래서 화면 코드는 한 벌만 짠다. Supabase가 멈춰 있어도 이 인터페이스로 화면 개발을 먼저 할 수 있다.
5. **탭으로 돌아오면 즉시 동기화**(visibilitychange visible → refresh).
6. **서버 불가 시 처리**: Supabase가 멈춰 방을 못 만들면 "문서를 열 수 없습니다" + "연습 문서 열기"를 띄운다. /pae처럼 봇 데모로 몰래 바꾸지는 않는다.

### 2-4. 응답 속도 [추정]

Vercel 함수 지역은 싱가포르(`sin1`)다 [확인: vercel.json]. Supabase 지역은 모른다(기획서 §9). 발사 한 번은 토큰 확인 → 상태 읽기 → 저장으로 서버 안에서 왕복 3번이 생긴다. 따뜻한 상태에서 0.3~0.6초, 함수가 식어 있으면 그 이상으로 본다. 상태줄의 "계산 중..."이 이 대기 시간을 가린다. 함수가 덜 식게 하려면 API를 여러 개로 나누지 말고 `action` 하나로 합치는 편이 낫다(백엔드에 제안, §8).

## 3. 숨기기(Tab / ESC / 창 이탈)

**난이도: 중.** 코드는 200줄 안팎이지만 함정이 많고, 실제 기기(맥 한글 입력기, 윈도우, 아이폰)로 확인해야 끝난다.

### 3-1. 동작 규칙 [제안 — 기획팀장 확인 요청]

1. **숨기기는 한 방향이다.** 게임 화면에서 Tab이나 ESC를 누르면 위장 시트로 간다. 위장 시트에서 Tab은 "다음 칸", ESC는 "편집 취소"로만 동작하고 **절대 게임으로 돌아가지 않는다.** 허둥대며 두 번 누르면 토글 방식은 게임을 다시 띄운다. R2 창의안의 "다시 ESC로 복귀"는 채택하지 않는다.
2. **복귀는 하단 시트 탭에서 게임 시트를 클릭할 때만**(휴대폰은 탭). 스프레드시트에서 시트를 바꾸는 평범한 동작이라 옆에서 봐도 자연스럽다. 창으로 돌아와도 자동으로 게임이 뜨지 않는다.
3. **보조키**: Ctrl·Alt·Cmd가 같이 눌린 Tab/ESC는 무시한다(PM 확정). **Shift+Tab은 숨긴다.** OS 단축키가 아니고, 급할 때 Shift가 같이 눌리기 쉽다. Ctrl+Tab(브라우저 탭 전환)과 Alt+Tab·Cmd+Tab(앱 전환)은 페이지가 키를 받지 못하지만, 창을 벗어나는 순간 자동으로 숨는다.
4. **적용 범위**: 격자가 보이는 화면(대기, 배치, 대전, 결과, 연습)에서는 Tab과 ESC가 모두 숨기기다. 랜딩과 입장 양식(업종·닉네임 입력)에서는 ESC만 숨기기이고 Tab은 원래대로 입력 칸을 옮긴다. 이 화면들은 입력 칸 이동이 필요하고, 랜딩은 게임임을 숨기지 않는 화면이기 때문이다.

### 3-2. 구현 방식

1. `window`에 keydown 리스너를 캡처 단계로 하나만 단다. 이름 상자나 퀴즈 답 칸에 포커스가 있어도 먼저 받고, `preventDefault`로 브라우저의 포커스 이동을 막는다.
2. 키 판별은 `e.key`와 `e.code`를 둘 다 본다. 한글 입력기가 글자를 조합하는 중이면 key가 "Process"(keyCode 229)로 오는 경우가 있다 [추정]. 조합 중(`isComposing`)이어도 숨긴다.
3. **화면 전환은 React 렌더링을 거치지 않는다.** 핸들러 안에서 `.mc-shell`의 `data-view` 속성을 바로 바꾸고, CSS가 두 레이어 중 하나를 `display:none`으로 감춘다. React 상태는 그 뒤에 따라 바뀐다. 전환 애니메이션과 transition은 0이다.
4. **위장 시트는 방에 들어올 때 미리 그려 둔다**(숨긴 채로 마운트). 처음 숨길 때 분할된 코드 파일을 내려받거나 30행을 새로 계산하면 0.1초를 넘길 수 있다. 위장 숫자는 방·사용자별 seed로 한 번만 만든다. 그래야 다시 숨겨도 같은 숫자가 보인다. 볼 때마다 숫자가 바뀌면 그게 티다.
5. 숨기기 직전에 포커스가 있던 요소를 기억하고 blur한 뒤, 포커스를 위장 시트의 선택 칸으로 옮긴다. 돌아오면 원래 요소로 되돌린다. 퀴즈에 치던 숫자는 그대로 남는다.
6. **창 이탈**: `blur`, `visibilitychange(hidden)`, `pagehide` 세 이벤트가 같은 숨기기 함수를 부른다. 여러 번 와도 한 번만 처리된다.
7. **0.1초 측정 방법**(기획서에 없음): keydown의 `e.timeStamp`부터 전환 후 다음 프레임(rAF)까지를 `performance.measure('mc-hide')`로 남긴다. QA는 개발자 도구에서 읽는다. 목표는 p95 50ms 이하(기준 100ms)다.
8. 서버 보고(view_state)는 전환 뒤에 비동기로 보낸다.

### 3-3. 함정 목록

| 함정 | 증상 | 대응 |
|---|---|---|
| 토글 방식 | 두 번 누르면 게임이 다시 뜬다 | 한 방향(3-1) |

## 4. 업종 문구 JSON, 공용 격자 엔진, 상태 관리

### 4-1. 업종 팩

- 파일: `copy/accounting.json`, `copy/sales.json`, `copy/hr.json`, 업종과 무관한 문구는 `copy/common.json`.
- **네트워크에는 업종 번호(0/1/2)만** 입장할 때 보낸다(측정용). 서버는 한국어 문장을 보내지 않고 **이벤트 코드와 숫자만** 보낸다. 문장은 각자 자기 브라우저의 업종 팩으로 만든다.
- 그 결과 같은 사건이 두 화면에서 다른 말로 보인다. 결과 메모는 그래도 괜찮다. 하지만:
  - **도발 문구는 common.json에 둬야 한다.** 업종 팩에 두면 보낸 사람과 받은 사람이 서로 다른 문장을 본다(§7-2).
  - **배는 길이 슬롯(L4/L3/L2)으로만 구분**하고, 이름은 보는 사람의 팩에서 가져온다.
  - **퀴즈**: 서버는 표 숫자와 `labelSeed`만 보낸다. 문장은 각자 `labels[seed % 개수]`로 고른다.
- 스키마(주요 필드): 파일명 기본형, 시트 탭 이름 3개, 배 이름(길이별 후보 3개 + 판 위에 쓸 2~3자 약어), 빗나감·명중·침몰 메모, 퀴즈 라벨 20개 이상, 퀴즈 표 머리글, 결과 문서(패·승·무, 경보 실패 한 줄), 경보 토스트 4~5개, 위장 시트 생성 규칙(열 10개 정의, 행 항목 목록, 숫자 범위, 소계 간격, 차트 열).
- **자동 검사(테스트)**: zod 스키마 + 문구 검사 테스트를 둔다. 개수, 금지어(비평 R2 §3-3 목록 + "Battleship·배틀십·Excel·엑셀·Microsoft·Google"), 셀 폭을 넘는 글자 수(디자인이 정한 열 너비 기준), 약어 2~3자, 도발 문구의 "당신" 같은 2인칭을 걸러 낸다. G0-6 검수 중 기계로 잡을 수 있는 부분을 미리 막는 것이다. 웃긴지 아닌지는 사람이 본다.
- 문구 고르기(`pick.ts`): 한 판 안에서는 같은 문구를 다시 쓰지 않는다. "최근 3판 회피"(localStorage)는 일정이 밀리면 가장 먼저 뺄 항목이다.
- 번들: 3개 팩을 정적으로 다 넣는다. 고른 업종의 위장 시트는 즉시 떠야 하므로 나중에 불러오기(lazy load)를 하지 않는다. 크기는 빌드 결과로 확인한다.

### 4-2. 공용 격자 엔진 (두 겹)

1. **`sheet-model.ts`(순수 리듀서)**: 선택, 방향키 이동, Tab·Enter 이동, 편집 시작·확정·취소, A1 주소, 범위 문자열을 다룬다. 게임판은 읽기 전용으로, 위장 시트는 편집 가능으로 같이 쓴다. 단위 테스트 대상이다.
2. **`SheetGrid` 컴포넌트**: 열 문자·행 번호 머리글, 고정 머리행, 셀 렌더러를 props로 받는다. **판 바깥의 빈 셀은 DOM이 아니라 CSS 배경 격자선으로 그린다.** 그래서 "판 바깥에도 셀이 이어진다"(기획 Q1)를 노드 0개로 처리한다.
3. **위장 시트**: 생성기(seed, 업종 규칙) → 30행×10열을 만들고 소계와 합계가 실제로 맞게 한다. 숫자 칸을 고치면 정해진 열 규칙대로 소계·합계를 다시 계산한다. **범용 수식 파서는 만들지 않는다.** 막대 차트는 한 열을 묶은 CSS 막대다. 저절로 바뀌는 칸은 현재 시각과 마지막 저장 시각뿐이다.
4. **게임 엔진(`engine.ts`)**: 백엔드 소유의 순수 함수다. 연습 모드가 "1척이 이미 침몰한 상태"에서 시작하므로, 아무 초기 상태나 받아서 이어갈 수 있어야 한다.

### 4-3. 상태 관리

| 종류 | 어디에 | 예 |

## 5. 휴대폰 처리 (Tab 키 없음)

- **판별**: 배치는 화면 폭(768px 미만이면 탭 전환 배치)으로 정한다. 숨기기 버튼은 `(pointer: coarse)`일 때 보인다. 키 핸들러는 항상 켜 둔다(아이패드 + 키보드면 Tab이 그대로 동작).
- **숨기기**: 하단 시트 탭 줄에 위장용 시트 탭(예: "요약")을 늘 보이게 둔다. 한 번 탭하면 숨고, 게임 시트 탭을 누르면 돌아온다. **데스크톱의 복귀 방식과 같아서** 연습에서 한 번만 알려 주면 된다.
- **자동 숨기기**: 앱 전환, 화면 잠금(`visibilitychange`, `pagehide`).
- **판**: 행 머리글 포함 9열이면 360px 폭에서 칸이 약 38px다. 터치하기에 충분하다. "내 판 / 쏜 기록" 탭은 **내 차례가 오면 "쏜 기록"으로만 자동으로 바꾼다.** 상대가 쏜 곳은 상태줄에 한 줄로 알린다. 화면이 제멋대로 왔다 갔다 하면 헷갈린다.
- **발사**: 탭하면 칸이 선택되고, 수식 입력줄의 확인(✓) 버튼을 눌러야 발사된다. 잘못 쏘는 것을 막기 위해서다. 데스크톱도 같은 원리로 "클릭은 선택, Enter나 더블클릭은 발사"를 제안한다(§7-6, 디자인 확인).
- **메모**: 휴대폰은 마우스를 올릴 수 없다. 이미 쏜 칸을 탭하면 메모를 화면 아래 한 줄로 보여 준다.
- **퀴즈**: `inputMode="numeric"`. 키보드가 올라와도 문제 표가 가려지지 않게 화면에 보이는 영역(visualViewport) 위에 고정한다. 키보드 여는 시간까지 10초에 들어가므로 휴대폰이 불리할 수 있다. 플레이테스트에서 확인한다.
- **배치**: 배를 탭 → 칸을 탭 → 회전 버튼. "자동 배치"를 크게 둔다. 끌어다 놓기는 만들지 않는다.
- **"위장 단순화"의 정의**(기획서에 정의가 없음): 휴대폰의 위장 시트는 스크롤과 칸 선택만 되고 편집은 안 된다.
- `100dvh`와 안전 영역(safe-area)을 반영한다. 경보 토스트가 숨기기 탭을 가리지 않게 한다.

## 7. 기획서에서 프론트 관점으로 모순되거나 과한 부분

1. **두 판 나란히 vs "열 A~H가 그대로 좌표" vs "판 바깥에도 빈 셀이 이어짐"**(§1 화면, Q1). 하나의 이어진 시트에 판 두 개를 나란히 놓으면 오른쪽 판은 J~Q열이 된다. 그러면 "B7"로 쏠 수 없다. 해결안: (가) **창 나누기처럼 판마다 A~H 머리글을 따로 단 두 칸 화면**, 또는 (나) 쏘는 판을 크게 두고 내 판은 오른쪽의 작은 참조 창으로. 디자인팀장이 정하고, 프론트는 (가)를 추천한다.
2. **도발 문구가 업종 팩 안에 있음**(A-6) vs **업종은 각자 고름**. 같은 번호의 도발이 두 화면에서 다른 문장으로 보인다. 도발은 `common.json` 한 벌로 옮기자.
3. **"퀴즈 정답이 브라우저에 오지 않게"**(§2 판결 4, G0-4, A-7). 화면에 숫자 세 개를 보여 줘야 하므로 정답(합계·부가세·차액)은 언제나 바로 계산할 수 있다. 정답을 빼고 보내는 건 상관없지만 보안 점검 항목으로 둘 이유는 없다. **G0-4는 "상대 배 위치"에 집중하자.**
4. **"계산기와 엑셀도 써도 된다"**(§4) vs **"창을 벗어나면 자동 위장"** vs **10초**. 계산기 앱으로 가는 순간 숨고, 돌아와서 시트 탭을 누르는 데 1~2초를 잃는다. 결국 계산기를 쓴 사람이 손해를 본다. 안내 문구를 "암산으로 풀 수 있는 수준"으로 바꾸자. 선택안(P1)으로 답 칸에 `=47+38+21`처럼 칠 수 있게 하면 "이 시트가 곧 엑셀"이 되어 웃음 포인트도 된다.
5. **"ESC 시트"·경보 배너의 "[ESC]" 표기**(§1, §1 웃음 장치, A-5). Tab이 주 키로 확정됐으니 배너 표기는 "[Tab]"으로, 문서 용어는 "숨기기 시트"로 통일하자. 숨긴 뒤 돌아오는 방법은 기획서에 없다. §3-1의 한 방향 규칙과 시트 탭 복귀를 방향서에 넣어 달라.
6. **"셀을 클릭하면 발사"**(§1 ④). 스프레드시트에서 클릭은 "선택"이다. 일하는 척 칸을 이리저리 누르거나 실수로 한 번 클릭해도 한 발이 나간다. **클릭은 선택, Enter나 더블클릭은 발사, 휴대폰은 선택 + ✓**를 제안한다. 더블클릭은 원래 "편집"이라 "확정"으로 읽혀 자연스럽다.
7. **tick 2~3초 + "last_seen 3초 이내"**(A-3). 멀쩡한 사람이 계속 끊긴 것으로 판정된다(§2-2 #4). 기준을 tick 간격의 2배 이상으로 바꿔 달라(백엔드 판단).
8. **API 목록 누락**(A-1). view_state 보고, 방 만들기(POST rooms), 도발 보내기, 피식 응답·문구 신고, 퀴즈 "표시됨" 확인 경로가 없다. 동시 정답 0.2초 판정은 첫 정답 응답이 바로 결과를 줄 수 없다는 뜻이다. 응답은 "판정 중"이고, 확정은 상태 갱신으로 온다. 이 흐름도 계약에 넣어 달라.

**그 밖에 가벼운 것**
- "탭 제목 고정"과 "v8로 저장"은 충돌하지 않는다. 고정의 뜻은 "숨기거나 차례가 바뀌어도 그대로"다. 재대결 때 버전 숫자만 바뀐다.
- 랜딩 탭 제목도 파일명 모양으로 두자. 랜딩 화면을 열어 둔 채로도 티가 나지 않게 하려는 것이다. 본문에서는 게임임을 분명히 밝히니 §6 원칙과 부딪치지 않는다. noindex라 검색 노출 손해도 없다(공개 단계에서 다시 정한다).
- "베타" 표시는 랜딩과 결과 문서 꼬리에만 둔다. 게임 시트 안에 두면 그게 티다.
- 30분 재접속은 같은 브라우저(같은 익명 세션)에서만 된다. 다른 기기나 브라우저로는 못 돌아온다. FAQ에 한 줄 적자. 또 같은 브라우저의 탭 두 개는 같은 사람으로 잡힌다. QA와 PM이 혼자 테스트할 때는 시크릿 창이나 다른 브라우저를 써야 한다.
- 링크 미리보기 이미지는 업종 구분 없이 한 장으로 둔다. 서버는 보낸 사람의 업종을 모른다.

## 8. 다른 팀장에게 요청

**디자인팀장**
1. 판 배치: §7-1의 (가) 판마다 머리글을 단 두 칸 화면 / (나) 큰 판 + 작은 참조 창 중 결정.
2. 복귀 동작은 시트 탭 클릭, 숨기기는 한 방향. 경보 토스트 표기는 "[Tab]".
3. 클릭은 선택, Enter·더블클릭은 발사, 휴대폰은 ✓ 확인.
4. 명중·빗나감·침몰을 색 말고 글자로도 구분하는 표기.
5. 포커스·선택 표시는 시트식 테두리로(전역 주황 링 대체).
6. 글꼴: 시스템 UI 글꼴(맥 Apple SD Gothic Neo, 윈도우 맑은 고딕)과 Pretendard 중 무엇이 "시트 같은지" 결정. 프론트는 시스템 글꼴을 추천한다.
7. 열 너비와 열별 최대 글자 수. 이 값이 문구 검사 테스트의 기준이 된다.
8. 휴대폰 숨기기 탭의 이름과 위치.

**백엔드팀장**
1. D0에 `types.ts` 공동 고정. 공개 상태에 단조 증가 `ver`, 모든 응답에 `now`, 기한은 절대 시각(서버 ms), 숨은 시간 남은 예산 포함.
2. 내 배, 받은 힌트 값, 퀴즈 잠금은 본인만 읽는 RLS 행에(재접속 복원용).
3. 서버는 한국어 문장 없이 이벤트 코드와 숫자만. 오류는 코드로.
4. view_state는 tick 본문 + 바뀔 때 즉시 보고. last_seen 기준은 tick 간격의 2배 이상.
5. 기한 처리는 심판 1명이 아니라 누구의 tick이든 처리하고 `ver` 비교 후 저장으로 중복 방지.
6. 여러 액션(place·fire·quiz·hint·alarm·taunt·rematch·view)을 `action` 라우트 하나로 합치는 안 검토(함수가 덜 식고, zod 유니언 하나로 검증).
7. 동시 정답 0.2초 판정의 응답 흐름("판정 중" → 상태로 확정).
8. 화면이 사라질 때 자동 leave를 쓰지 않는다는 점 공유. 방 만료로 정리.
