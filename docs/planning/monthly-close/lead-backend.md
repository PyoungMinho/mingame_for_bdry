## 0. 결론 (먼저 읽을 것)

1. **판정·상태·시계는 전부 Vercel API(서버리스 함수)가 맡는다. Supabase는 저장소 겸 "초인종"(변경 알림)으로만 쓴다.** 브라우저는 DB를 직접 읽지 않는다. 그래서 RLS는 "전부 거부" 한 줄로 끝나고, 상대 배·퀴즈 정답이 브라우저로 갈 수 있는 길은 API 응답 하나뿐이다. 그 응답은 테스트로 막는다.
2. **기준 시계는 서버 시각 하나다.** 모든 기한(턴 20초, 퀴즈 10초, 경보 3초 판정 창)은 절대 시각으로 상태에 저장한다. 기한 처리는 cron 없이 "다음 요청이 들어올 때 지난 기한부터 처리"하는 방식이다. 브라우저 시계는 카운트다운 표시에만 쓰고, 서버 시각과의 차이를 보정한다.
3. **기획서 대비 바꾸자는 것이 9가지 있다(§1).** 가장 큰 것은 ① /pae의 익명 로그인 대신 브라우저마다 비밀키를 쓰는 자체 신원 방식, ② 테이블 6개를 4개로 줄이는 것(숨긴 정보를 방 1행에 몰고 RLS 전부 거부), ③ 퀴즈 "먼저 맞힘"을 사람마다 "문제를 받은 시각부터 걸린 시간"으로 재는 것이다. PM 확정 사항은 하나도 건드리지 않는다.
4. **Supabase 복구 전망은 기획서보다 낫다.** 2026-11-07 기준 공식 문서는 "멈춘 지 **1년** 안이면 대시보드에서 다시 켤 수 있다"고 적고 있다 [확인]. 기획서의 "90일"은 예전 기준으로 보인다. /pae가 2026-06월 말에 만들어졌으므로 다시 켜기가 될 가능성이 높다 [추정]. 안 되면 §10-3의 새 프로젝트 절차를 따른다. 이때 /pae·/dongne까지 영향을 받는다.
5. **새 환경변수는 0개다.** 기존 3개(`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`)와 Vercel이 자동으로 넣어 주는 `VERCEL_ENV`만 쓴다.
6. **가장 큰 리스크는 기술이 아니라 공유 자원이다.** Supabase 프로젝트 하나와 Vercel 무료 한도 하나를 /pae·/dongne·/exam 등이 같이 쓴다. 월마감이 멈추면 다른 앱도 같이 멈추고, 반대도 마찬가지다(§13).
7. 백엔드 일정은 **D0 계약 동결(팀장) → D1 API·DB 설계자 병렬 → D2 통합·보안 점검 → D3 QA 대응**, 약 3일이다. PM의 SQL 실행은 D2에 한다.

## 3. 시스템 구조도

```
 [브라우저 A]                                  [브라우저 B]
   │  localStorage: 비밀키, 테스트 표시            │
   │                                               │
   ├─ HTTPS ──► Vercel 함수 /api/monthly-close/* ◄─ HTTPS ─┤   ← 핵심 경로(vercel.app 하나만 열리면 동작)
   │            (sin1) 판정·상태 전이·시계·검증·투영(view)   │
   │                  │                 │                  │
   │                  │ service key     │ 초인종 발송({v})   │
   │                  ▼                 ▼                  │
   │        Supabase Postgres     Supabase Realtime        │
   │        mc_rooms/mc_players   Broadcast topic          │
   │        mc_matches/mc_events  "mc:<방 UUID>"           │
   │        (RLS 전부 거부)              │                  │
   └──────── WebSocket(선택) ◄───────────┴──────► WebSocket(선택) ┘

 [박대리 연습] 브라우저 안에서만 엔진 실행. 서버·DB 미사용, 지표 제외.
```

**책임 분담**
- **Vercel API가 하는 일**: 상태 전이 전부(배치 검증, 발사 판정, 라운드·무승부·상한, 퀴즈 출제·채점·지급, 힌트 계산, 경보 출제·판정, 시간 초과, 부재 처리, 재대결), 기한 처리, 보는 사람별 화면 데이터 만들기(투영), 지표 기록.
- **Supabase가 하는 일**: 방 상태를 오래 보관하는 단일 원본, 동시 저장 충돌 감지(버전 비교), 초인종 전달. DB 안에 게임 규칙(plpgsql)을 두지 않는다. 규칙이 TS와 SQL 두 곳으로 갈라지면 테스트가 둘로 쪼개지기 때문이다.
- **브라우저가 하는 일**: 그리기, 입력, 위장 전환(0.1초, 서버를 기다리지 않음), 경보 반응 시간 측정(신뢰함, 기획서 판결 4 "적정선"), 카운트다운 표시.

**지연 예산** [추정]: 한국↔sin1 왕복 약 70~90ms. Supabase도 싱가포르면 DB 왕복은 1~2ms라 액션 1회가 약 120~180ms다. Supabase가 서울이면 DB 왕복이 회당 약 70ms씩 붙어 약 300~400ms가 된다. 이 경우 sync를 "접속 신호 + 버전 조회"를 한 번에 처리하는 DB 함수 1개(RPC)로 줄이는 최적화를 쓴다(DB설계자 선택 과제). 기존 프로젝트의 지역은 [미확인]이라 PM이 대시보드에서 확인해야 한다.

## 4. 상태·시계·동시성 규칙 (API설계자에게 넘길 기준)

### 4-1. 상태는 한 덩어리
- `mc_rooms.state`(JSON) 하나에 공개 부분과 비밀 부분(`secret.boards`, `secret.quizAnswer`, `secret.alarmRound`)을 함께 둔다. 이 행은 브라우저가 절대 직접 읽지 못한다.
- 브라우저에 가는 것은 오직 `viewFor(state, seat)`의 결과다. 이 함수는 **허용 목록 방식으로 새 객체를 만든다**(원본을 복사한 뒤 비밀을 지우는 방식은 금지). 상대 판에서 보내는 것은 "내가 쏜 칸의 결과(명중·빗나감·침몰)"와 "침몰한 배의 칸"뿐이다.
- 상태에는 `version`(정수)을 함께 둔다. 저장은 "읽을 때의 version과 같을 때만 UPDATE, 성공하면 +1"이다. 실패하면 다시 읽고 다시 적용하며 최대 3회 시도한다. 동시 상황(같은 칸 두 번 클릭, 두 사람 동시 정답, 발사와 시간 초과 겹침, 경보와 시간 초과 겹침)은 전부 이 하나의 규칙으로 줄을 세운다.
- 모든 액션에는 브라우저가 만든 `actionId`를 붙인다. 같은 id가 다시 오면 다시 적용하지 않고 최신 화면만 돌려준다. 더블클릭과 재전송 때 에러가 잠깐 깜빡이는 것을 막는다.
- 접속 신호(`last_seen`, `view_state`)는 `mc_players`에 따로 둔다. 2초마다 오는 접속 신호가 게임 상태의 version을 올려 진짜 액션과 충돌하는 일을 막기 위해서다.

### 4-2. 시계
| 항목 | 규칙 |
|---|---|
| 기준 시계 | 판정에 쓰는 모든 시각은 **Vercel 함수의 서버 시각 하나**로 통일한다. DB의 `now()`는 기록용(`created_at`)으로만 쓴다 |
| 저장 방식 | 기한은 절대 시각(ms)으로 저장한다: `turnDeadlineAt`, `quiz.deadlineAt[seat]`, `alarm.issuedAt` |
| 표시 | 모든 응답에 `serverNow`를 넣는다. 브라우저는 "서버 시각 − 내 시각(왕복의 절반 보정)"으로 오프셋을 구해 카운트다운에만 쓴다. 사용자 PC 시계가 몇 분 틀려도 판정에는 영향이 없다 |
| 기한 처리 | **cron 없음.** sync나 액션 요청이 오면 먼저 "지난 기한"을 처리한다. 한 요청에서 시간 초과는 **최대 1회만** 처리하고, 다음 기한은 "지금 + 20초"로 다시 잡는다. 둘 다 끊겼다가 10분 뒤 돌아와도 턴이 연쇄로 넘어가지 않는다 |
| 턴 20초 | 차례인 사람의 `view_state`가 `disguise`(숨기기 중)면, 숨기기를 풀 때 숨어 있던 시간만큼 기한을 늦춘다. 판당 누적 120초까지. 숨기기 시작·해제는 브라우저가 **바로** 보고한다(다음 sync를 기다리지 않음) |
| 시간 초과 | 그 발은 넘어간다. 3번 연속이면 상대 화면에 "부재 처리(기권승)" 버튼이 생긴다. 접속이 끊긴 사람도 같은 규칙을 적용받는다(30초짜리 순단은 한두 발 손해로 끝나고 판은 살아 있음) |

### 4-3. 퀴즈 (4·8·12라운드, 규칙은 기획서 그대로)
1. **출제 조건**: 라운드 시작 시점에 두 사람 모두 `view_state=game`이고 `last_seen`이 3초 이내일 것. 아니면 다음 라운드로 미룬다.
2. **배달 시각**: 서버가 그 사람의 응답(sync든 액션이든)에 문제를 처음 실어 보낸 시각을 `deliveredAt[seat]`로 기록한다. 2초 안에 배달되지 않은 사람은 기획서대로 "출제 시각 + 1초"를 배달 시각으로 본다.
3. **마감**: 사람마다 `deliveredAt[seat] + 10초`.
4. **오답**: 그 사람에게만 `#VALUE!`와 `lockUntil = 지금 + 3초`를 보낸다. 상대 화면에는 아무것도 보내지 않는다. 잠금 중에 낸 답은 거부한다.
5. **판정**: 정답을 낸 사람마다 `경과 = 서버 수신 시각 − deliveredAt[seat]`을 계산해 작은 쪽이 이긴다. 차이가 0.2초 이하면 둘 다 받는다. 1인 최대 2개 한도와 "검토 완료로 빠지기"는 엔진에서 처리한다.
6. **확정 시점**: 먼저 맞힌 사람이 나와도, 상대가 이길 가능성이 남아 있는 시각(`상대 deliveredAt + 먼저 맞힌 사람의 경과 + 0.2초`)까지는 결과를 미룬다. 서버는 `settleAt`을 내려주고, 두 브라우저가 그 시각에 sync를 한 번 보내 확정시킨다. 기다리는 동안 상태줄은 "계산 중..."이다(위장과도 맞음).
7. **한계(수용)**: 정답은 숨기지만, 문제의 숫자를 보면 누구나 계산할 수 있다. 개조한 클라이언트가 자동으로 답을 내는 것은 막을 수 없다. 친구끼리 하는 게임이라 수용한다.

### 4-4. 결재 경보
- 서버가 판을 시작할 때 6~15라운드 중 하나를 무작위로 골라 비밀 상태에 넣는다. 출제 조건은 퀴즈와 같고, 퀴즈가 진행 중이면 미룬다. 15라운드까지 조건이 한 번도 안 맞으면 그 판은 경보 없이 간다.
- 브라우저는 "배너가 뜬 시각 → 위장으로 바뀐 시각"(ms)을 보고한다. 서버는 3,000ms 이하인지만 판단한다(브라우저를 신뢰함). 경보 당시 `last_seen`이 3초를 넘었던 사람은 벌칙에서 뺀다. 10초 안에 보고가 없고 접속 중이었다면 실패로 본다.
- 실패하면 `penaltySkipNext[seat] = true`로 두고, 그 사람의 다음 차례는 자동으로 넘긴다. 방 설정 `alarmOn=false`면 아예 출제하지 않는다.

### 4-5. 도발·힌트·로그
- 도발은 정해진 문구 id만 받는다(자유 입력 없음). 3턴에 1번 제한은 서버가 강제한다.
- 힌트 값(범위 안의 배 칸 수)은 서버가 상대 비밀 판으로 계산해 **요청한 사람의 비공개 영역**에만 저장한다. 상대에게는 "변경 내역"에 범위만 남긴다("편집자 A님이 E열을 검토했습니다").

## 5. API 방향 (초안, 라우트 파일 6개)

기획서 A-1의 9개 라우트(`join, place, fire, quiz, hint, alarm, tick, rematch, leave`)를 **조회·접속 신호용 `sync`와 상태 변경용 `action` 하나씩으로 합친다.** 인증 → 읽기 → 엔진 → 버전 비교 저장 → 초인종 → 투영으로 이어지는 같은 처리 과정을 9번 복사하면 버그도 9곳에 생기기 때문이다.

| # | 메서드·경로 | 하는 일 | 주요 입력 | 주요 출력 |
|---|---|---|---|---|
| 1 | `POST /api/monthly-close/rooms` | 방 만들기 | 닉네임, 업종 번호(0~2), 경보 켜기 여부, (헤더) 비밀키·테스트 표시 | 방 번호, 내 자리, 화면 데이터, `serverNow` |
| 2 | `POST /api/monthly-close/rooms/[code]/join` | 입장·재입장 | 닉네임, 업종 번호 | 내 자리, 화면 데이터 |
| 3 | `POST /api/monthly-close/rooms/[code]/sync` | 접속 신호, 화면 상태(`game`/`disguise`) 보고, 지난 기한 처리, 변경 확인 | 내가 아는 version, 화면 상태, (경보 중이면) 반응 ms | 변경이 없으면 `{version, serverNow}`만, 있으면 화면 데이터 전체 |
| 4 | `POST /api/monthly-close/rooms/[code]/action` | 상태 변경(종류별 분기) | `actionId`, `type` = `place`(배 3척) / `fire`(칸) / `answer`(퀴즈 id, 값) / `hint`(종류, 범위) / `alarm`(반응 ms) / `taunt`(문구 id) / `rematch` / `resign`(기권) / `claimAbsent`(부재 처리) / `leave` | 화면 데이터 |
| 5 | `POST /api/monthly-close/feedback` | "피식했나요?", 불편 문구 신고 | 매치 id, `laugh` 또는 문구 id | 204 |
| 6 | `GET /api/monthly-close/health` | DB 연결과 테이블 존재만 확인(비밀 없음, 캐시 금지) | 없음 | `{db: "ok" | "down"}` |

**계약 원칙**
- 인증은 헤더 `x-mc-key`(비밀키)로 한다. **URL에는 절대 넣지 않는다**(주소는 공유되고 로그에도 남는다). 커스텀 헤더를 쓰므로 CSRF(다른 사이트가 몰래 요청을 보내는 공격)도 자연히 막힌다.
- 에러 코드: `ROOM_UNAVAILABLE`(없는 방과 꽉 찬 방에 같은 메시지 "문서를 열 수 없습니다"를 보내 방이 있는지 없는지 알려주지 않음), `NOT_YOUR_TURN`, `LOCKED`(퀴즈 잠금), `RATE_LIMITED`, `SERVICE_DOWN`(503, DB 연결 불가). 거부할 때도 최신 화면 데이터를 같이 보내 브라우저가 바로 다시 맞추게 한다(/pae의 "stale 거부 후 재동기화"와 같은 효과 [확인]).
- 화면 데이터(view) 초안 — **D0에 팀장이 타입으로 고정하고 프론트에 넘긴다**:
  - `room`: 방 번호, 상태(`waiting`/`placing`/`playing`/`ended`), version, 경보 설정, 판 순번(v7·v8), `serverNow`
  - `me`: 자리, 닉네임, 업종 번호, 내 배, 배치 완료 여부, 남은 숨기기 시간, 내 힌트(종류·범위·값), 퀴즈 잠금 해제 시각, 다음 발사 쉼 여부
  - `opp`: 자리, 닉네임, 업종 번호, 접속 여부, 숨기기 중 여부(시계가 멈춘 이유를 보여 주기 위해), 배치 완료 여부
  - `game`: 라운드, 차례, 턴 기한, 내가 쏜 칸 결과, 상대가 쏜 칸 결과, 침몰 수, 마지막 사건(결과 메모용 사건 종류 id), 변경 내역(힌트 범위·도발 문구 id), 퀴즈(id, 문제 숫자·라벨 id, 내 마감, 진행 상태, `settleAt`, 받은 사람), 경보(진행 중 여부, 출제 시각), 결과(승자 또는 무승부, 끝난 이유), 재대결 신청 현황
  - **들어가지 않는 것**: 상대 배 위치, 퀴즈 정답, 경보 예정 라운드, 상대의 힌트 값, 상대의 오답·잠금, 비밀키와 그 해시, 상대 기기 식별자
- 방 페이지는 상태를 서버에서 미리 그리지(SSR) 않는다. HTML에 상태가 섞여 나갈 길을 원천 차단한다.

**sync 주기(프론트와 합의할 것)**
| 상황 | 초인종 연결됨 | 초인종 안 됨 |
|---|---|---|
| 게임 중(배치·발사·퀴즈) | 2초(접속 신호 겸용) + 초인종 받으면 즉시 | 1초 |
| 대기방·결과 화면 | 5초 | 3초 |
| 탭이 숨겨짐(`document.hidden`) | 5초(접속 유지용) | 5초 |
| `settleAt`·턴 기한 도달 | 그 시각에 1회 즉시 | 같음 |

## 6. DB 방향 (초안, SQL은 DB설계자가 작성)

### 6-1. 테이블 4개 (`supabase/monthly-close-schema.sql`)
| 테이블 | 주요 칸 | 보관 | 비고 |
|---|---|---|---|
| `mc_rooms` | `id`(UUID, 기본키), `code`(5자리 숫자 문자, 고유), `status`, `version`, `state`(JSON: 공개+비밀), `settings`(경보), `created_at`, `updated_at`, `expires_at`(활동할 때마다 +30분), `env`(production/preview/development), `is_test` | 만료 후 삭제 | 비밀이 들어 있어 **어떤 읽기 규칙도 만들지 않음** |
| `mc_players` | `room_id`(→ `mc_rooms`, 함께 삭제), `seat`(0/1), `player_key`(비밀키의 SHA-256), `nickname`(8자), `industry`(0~2), `last_seen`, `view_state`, `joined_at` | 방과 함께 삭제 | 고유: (방, 자리), (방, player_key). 두 번째 고유 조건이 "같은 브라우저로 두 자리 차지"를 막는다 |
| `mc_matches` | `id`(UUID), `room_id`(외래키 없음, 방이 지워져도 남음), `seq`(판 순번), `rematch_of`, `host_key`, `player_keys`(2개), `started_at`, `ended_at`, `end_reason`(`sunk2`/`draw`/`cap`/`resign`/`absent`), `winner_seat`, `rounds`, `hints`(자리별 개수), `quizzes`(출제·풀이·경과ms 요약), `alarm_on`, `alarm_outcome`(자리별 통과/실패/제외), `env`, `is_test` | 90일 | 닉네임은 저장하지 않음. `ended_at`이 비어 있고 1시간이 지난 판은 "중도 이탈"로 본다(따로 마감 처리할 필요 없음) |
| `mc_events` | `id`(자동 증가), `at`, `type`, `room_id`, `match_id`, `player_key`, `props`(작은 JSON, 허용된 키만), `env`, `is_test` | 90일 | §9의 이벤트. 피드백과 신고도 여기 둔다(피드백은 매치·사람당 1건만 받는 부분 고유 조건) |

### 6-2. SQL 작성 원칙 (여러 번 실행해도 안전, 기존 테이블 무손상)
1. 모든 객체는 `mc_` 접두. `rooms`/`room_players`/`hands`/`dongne_dau`는 이름조차 쓰지 않는다.
2. `create table if not exists`, `create index if not exists`, `add column if not exists`만 쓴다. **`drop table`은 본 스크립트에 넣지 않는다.** /pae SQL은 다시 실행하면 테이블을 지우고 새로 만든다 [확인]. 그 방식을 따라 하지 않는다. 테이블을 지우는 작업은 `supabase/monthly-close-teardown.sql` 별도 파일로만 둔다.
3. 전체를 하나의 트랜잭션으로 묶는다. 중간에 실패하면 아무것도 바뀌지 않는다.
4. 4개 테이블 모두 RLS를 켜고 정책은 **하나도 만들지 않는다**(=익명 키로는 읽기·쓰기 전부 거부). 여기에 더해 `anon`·`authenticated` 역할의 권한도 회수한다(이중 잠금: 실수로 RLS가 꺼져도 권한이 없음).
5. Realtime 발행 목록에 테이블을 넣지 않는다(초인종은 Broadcast라 필요 없음).
6. 스크립트 끝에 **확인용 SELECT 1개**를 둔다. 테이블 4개가 있는지, RLS가 켜졌는지를 표로 보여 줘서 PM이 성공 여부를 눈으로 확인하게 한다.
7. 인덱스: `mc_rooms(expires_at)`, `mc_matches(started_at)`, `mc_events(type, at)`, `mc_events(player_key)`.
8. 게이트 판정 쿼리는 `supabase/monthly-close-gate.sql`(SELECT만)로 따로 둔다. /dongne의 `dongne-gate-query`와 같은 방식이다.

### 6-3. 정리와 용량
- cron은 쓰지 않는다. **방을 만들 때마다** 만료 방을 최대 50개 지우고, 90일 지난 매치·이벤트를 최대 500행 지운다. 함께 만든 MemoryStore로 이 동작도 테스트할 수 있다.
- 방 1개는 약 5~10KB [추정]이고 매치·이벤트는 판당 2~3KB [추정]다. 무료 500MB 기준으로 보면 지표 저장으로 용량이 차는 일은 사실상 없다. 용량을 채울 수 있는 경로는 "봇이 만든 방"뿐이고, 이는 §7의 전체 상한으로 막는다.

| 방 번호 | 10000~99999 범위에서 암호학적 난수로 뽑는다. 충돌하면 최대 5회 다시 뽑는다(/pae에는 이 재시도가 없음 [확인]). 대기방은 30분 동안 활동이 없으면 만료된다. 익명 키로 방 목록을 볼 길이 없다(/pae의 `rooms_read using(true)` 같은 전체 공개 읽기가 없음) | API설계자 + DB설계자 |
| 방 번호 | 추측 확률 [추정]: 대기방 10개가 동시에 열려 있고 시간당 360번 시도하면 시간당 약 4%. 친구 게임이고 최악의 결과는 "모르는 사람이 들어와 한 판 둠"이라 수용한다. 남용이 보이면 6자리로 올린다(코드 상수 하나만 바꾸면 됨) | 팀장 판단 |
| 남용 | ① 활성 방 전체 상한 200개(넘으면 "공유 서버 혼잡" 503) ② 비밀키당 방 만들기 10분 5회, 입장 실패 10분 20회, 액션 초당 10회 ③ 함수 인스턴스 메모리에서 IP당 방 만들기 시간당 30회(저장 안 함, 최선 노력) ④ 남용이 보이면 Vercel 방화벽 규칙 또는 Turnstile [미확인: 무료 플랜 제공 범위] | API설계자 |
| 입력 | zod로 칸(A~H×1~8), 배 모양(길이 4·3·2, 가로·세로, 겹침 금지), 문구 id(허용 목록), 업종(0~2), 반응 ms(0~10,000), 닉네임(1~8자, 제어문자 제거, 금칙어) 검증 | API설계자 |
| 자유 입력 | 닉네임 외에는 없음(채팅·자유 신고 없음). React가 이스케이프하므로 닉네임 XSS는 기본으로 막힌다 | 프론트 |
| 개인정보 | IP·User-Agent·쿠키·계정을 저장하지 않는다. 닉네임은 방이 만료되면 사라지고, 매치·이벤트에는 남기지 않는다. 보관은 90일. /privacy 재사용 여부는 Q4 때 함께 확인한다 | DB설계자 + 기획 |
| 노출 | noindex(메타 + `X-Robots-Tag`)와 베타 표시 | 프론트 |

## 8. 끊김·재접속·이탈

| 상황 | 처리 |
|---|---|
| 새로고침, 탭 닫았다 다시 열기 | 같은 브라우저면 비밀키가 그대로라 `join`이 기존 자리를 돌려주고, 서버 상태로 화면을 완전히 되살린다. 브라우저는 상태를 들고 있지 않는다. 배치 중이던 초안(아직 제출 전)만 sessionStorage에 임시 저장한다 |
| 30초 네트워크 끊김 | 판은 서버에 그대로 있다. 끊긴 동안 내 차례가 오면 시간 초과로 그 발만 넘어간다. 돌아오면 sync 한 번으로 상대 화면과 같아진다 |
| 상대 화면 표시 | `last_seen`이 5초를 넘으면 "다른 사용자 오프라인"으로 표시한다(상태줄 문구는 디자인팀 몫) |
| 3번 연속 시간 초과 | 상대에게 "부재 처리(기권승)" 버튼이 생긴다. 누르면 판이 끝나고(`end_reason=absent`) 완주로 세지 않는다 |
| 둘 다 끊김 | 기한 처리를 할 요청이 없으니 판이 그대로 멈춘다. 돌아오면 시간 초과는 최대 1회만 처리한다(§4-2) |
| 30분 동안 아무도 없음 | 방이 만료되고 다음 정리 때 지워진다. 매치는 "중도 이탈"로 집계된다 |
| 게임 중 "나가기" | 확인 창을 띄운 뒤 기권 처리한다(`resign`). 상대가 이긴다 |
| 대기방에서 방장이 나감 | 자리를 비우고 방은 만료를 기다린다. 손님은 "다른 동료와 한 판?"으로 새 방을 만든다(방장 승계 로직 불필요) |
| 같은 브라우저로 탭 2개 | 같은 사람으로 취급한다. 액션은 서버가 순서대로 처리한다. `view_state`는 마지막 보고를 따른다(한 탭은 숨기기, 한 탭은 게임 중이면 마지막에 보고한 탭 기준) [수용] |
| 브라우저나 기기 변경 | 재입장 불가. "같은 브라우저에서 다시 열어 주세요" 안내 |
| 재대결 "v8로 저장" | 두 사람이 모두 누르면 같은 방에서 판 순번 +1, 새 배치, `rematch_of` 기록. 2분 안에 상대가 누르지 않으면 "다른 동료와 한 판?"으로 안내 |

## 9. 게이트 측정 — 이벤트와 지표 연결

원칙: **원자적인 사건만 남기고, 지표 정의는 쿼리에서 한다.** 기획팀장이 지표 정의를 바꿔도 다시 배포할 필요가 없다.

### 9-1. 기록하는 이벤트 (`mc_events.type`)
| 이벤트 | 남기는 쪽 | props(허용 키만) |
|---|---|---|
| `room_created` | 서버 | 업종 번호, 경보 켬 여부 |
| `room_joined` | 서버 | 자리, 방장 키(누가 데려왔는지) |
| `match_started` | 서버 | 판 순번, 재대결 여부 |
| `match_ended` | 서버 | 끝난 이유, 라운드, 승자 자리 |
| `rematch_requested` | 서버 | — |
| `feedback` | 서버(브라우저 요청) | `laugh`(`none`/`some`/`lol`) |
| `line_report` | 서버(브라우저 요청) | 문구 id |
| `lines_shown` | 서버(브라우저가 판 끝에 1회 보냄) | 이번 판에 보여 준 문구 id 목록(신고율의 분모) |
| `share_copied` | 서버(브라우저 요청) | 문서 종류(시말서/품의서/경위서) |
| `transport` | 서버(브라우저가 세션당 1회) | 초인종 연결 성공·실패(회사망 차단 신호) |

매치 요약(힌트 수, 퀴즈 경과, 경보 결과)은 `mc_matches`에 판마다 한 번 쓴다.

### 9-2. 지표 → 쿼리 정의 (공통 조건: `env='production'` 그리고 `is_test=false`, 시딩 시작부터 14일)
| 지표 | 정의(초안, 기획팀장 확정 필요) |
|---|---|
| 볼륨 | 정상 종료(`sunk2`·`draw`·`cap`)된 매치 수 ≥ 100 / 매치를 시작한 서로 다른 `player_key` 수 ≥ 100 |
| 핵심① 입장률 | 2번 자리까지 찬 방 ÷ 만든 방 |
| 핵심② 완주율 | 첫 판이 정상 종료된 방 ÷ 2명이 찬 방(기권·부재·중도 이탈은 미완주) |
| 핵심③ 재대결률 | 두 사람 쌍 기준: 첫 정상 종료 후 24시간 안에 두 번째 판을 시작한 쌍 ÷ 한 판 이상 정상 종료한 쌍 |
| 핵심④ 전파 K | (완주 경험이 있는 사람이 연 방에 **처음 등장해서** 들어온 사람 수) ÷ (완주한 사람 수). 처음 등장 = 그 `player_key`의 첫 이벤트 |
| 웃음 | `feedback`이 30건 이상일 때 `some`+`lol` 비율 |
| 안전장치 | 문구별 `line_report` ÷ `lines_shown` > 3%, 경보 켠 판과 끈 판의 완주율 차이, `transport` 실패율 |

### 9-3. 한계 (게이트 문구에 반영 요청)
- `player_key`는 "사람"이 아니라 "브라우저"다. 한 사람이 회사 PC와 휴대폰으로 하면 2명으로 센다. 서로 다른 플레이어 수는 실제보다 조금 많게 나온다.
- "같은 기기끼리 한 판"은 다른 브라우저나 시크릿 창을 쓰면 구분할 수 없다(§1-6). PM·QA·배포 점검은 **반드시 테스트 표시를 켜고** 한다(숨은 주소 한 번 방문 → localStorage 표시 → 헤더로 전송 → 그 방과 그 방의 매치·이벤트가 모두 `is_test`).
- vercel.app 자체가 막힌 회사의 사용자는 아무 기록도 남기지 못한다. "회사에서 안 열린다 20%"는 서버로는 잴 수 없고 G0-2와 지인 응답으로만 판단한다.
- 로컬 개발과 프리뷰도 같은 Supabase를 쓰면 기록이 섞인다. `env` 칸으로 걸러낸다(`VERCEL_ENV`는 Vercel이 자동으로 넣는 값이고, 로컬은 `development`).
- **게이트 데이터는 Supabase 밖에 따로 보관한다.** 14일째에 gate SQL을 실행하고 그 결과를 `docs/planning/monthly-close/`에 남긴다. 그 뒤 프로젝트가 멈추거나 사라져도 판정 근거는 남는다.

## 10. Supabase 무료 플랜 — 멈춤과 두 가지 경우

### 10-1. 제약 요약
| 항목 | 값 | 출처 |
|---|---|---|
| 자동 멈춤 | 1주일 동안 DB 활동이 적으면 멈춘다. "하루 몇 번의 사용자 요청이면 보통 충분" | [확인: free-project-pausing 문서] |
| 사전 경고 | 멈추기 약 1주일 전에 경고 메일, 멈춘 뒤 확인 메일(조직 소유자 메일함) | [확인: 같은 문서] |
| 복구 기한 | 멈춘 지 **1년** 안이면 대시보드 "Resume project"로 데이터·설정 그대로 복구. 1년이 지나면 백업 파일을 받아 새 프로젝트에 복원 | [확인: 같은 문서 + restore 문서]. 기획서의 "90일"은 예전 기준으로 보임 |
| 활성 프로젝트 수 | 무료는 활성 2개 | [기획서 출처 인용, 재확인 안 함] |
| 그 밖 | DB 500MB, 데이터 전송 5GB/월, Realtime 동시 연결 200·메시지 200만/월 | [추정: 요약값, 재확인 안 함] |

### 10-2. 경우 A — 다시 켜기 성공 (가능성 높음 [추정])
PM 작업 순서(약 10분):
1. 메일함에서 "paused" 메일로 멈춘 날짜를 확인하고(참고용), 대시보드에서 프로젝트 → **Resume project**. 몇 분 걸린다.
2. 다시 켜진 뒤 확인 3가지: 프로젝트 주소가 조회되는지, **프로젝트 지역**(싱가포르/서울 등, §3 지연 판단용), Realtime 설정에서 공개 채널이 허용돼 있는지 [구현 시 확인].
3. SQL Editor에서 `supabase/monthly-close-schema.sql`을 1회 실행하고, 마지막 확인 표에 4개 테이블과 "RLS 켜짐"이 나오는지 본다(D2, DB설계자 SQL 확정 후).
4. 주소와 키가 그대로이므로 **Vercel 환경변수는 바꾸지 않는다.**
5. 바로 G0-2(회사망 확인)를 진행한다.

### 10-3. 경우 B — 다시 켜기 불가(삭제됨, 1년 초과, 버튼 없음)
**영향 범위: /pae, /dongne, /monthly-close 세 앱.** /exam·/moira 등 Supabase를 안 쓰는 앱은 영향 없음.
1. **같은 조직에 새 프로젝트를 만든다.** 지역은 **Southeast Asia (Singapore)**. Vercel 함수가 `sin1`이라 DB 왕복이 가장 짧다. 활성 2개 한도에 걸리면 다른 무료 프로젝트를 먼저 멈춰야 한다.
2. SQL 3개를 실행한다.
   - `pae-schema.sql`: 빈 프로젝트라 테이블을 지워도 손실이 없다. 단, **이 파일에는 /pae가 실제로 쓰는 `room_players.ready` 칸이 빠져 있다** [확인: 2026-07-07 커밋 fdc7398이 ready를 쓰는데 SQL에는 없음]. 칸을 추가하지 않으면 /pae 결과 화면의 "다음 라운드 준비"가 깨진다. /pae 담당이 파일을 먼저 고쳐야 한다.
   - `dongne-schema.sql`
   - `monthly-close-schema.sql`
3. Authentication → Anonymous 켜기(/pae용. 월마감은 필요 없음).
4. Vercel Production 환경변수 3개(`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`)를 새 값으로 바꾼다. **값을 바꾼 뒤 반드시 다시 배포해야 한다.** `NEXT_PUBLIC_` 값은 빌드할 때 번들에 박히고, 이미 만들어진 배포에는 새 값이 들어가지 않는다.
5. 잃는 것: /pae 진행 중 방(일시 데이터라 무관), /dongne DAU 기록(SQL을 실행한 적이 없다면 애초에 없음 [미확인]), /pae 익명 사용자(새 uid를 받으므로 무관).
6. 다시 배포한 뒤 /pae 방 만들기, /dongne ping, 월마감 health를 모두 확인한다(배포엔지니어).

### 10-4. 멈춤 재발 방지 (시딩 14일 이후 포함)
- **시딩 14일 동안**: 실제 플레이 트래픽이 있어서 멈추지 않는다 [추정]. 월마감 트래픽 덕분에 /pae·/dongne도 같이 살아 있게 된다.
- **14일째(게이트 판정일)**: ① gate SQL 결과를 docs에 저장한다(§9-3) ② PM이 정한다:
  - Go → Pro 전환($25/월, 멈추지 않음) 또는 아래 "깨우기" 선택
  - 1회 조정·접기 → 무료 유지. 멈추면 경고 메일을 받고 필요할 때 다시 켠다. 멈추면 세 앱이 모두 꺼진다는 점을 PM이 알고 있어야 한다.
- **깨우기(keepalive) 선택지 — 기본안은 쓰지 않음(기획서 유지), PM 판단 사항**: 공식 문서는 경고를 받은 뒤 "연결된 앱으로 API 요청을 보내는 것"을 멈춤을 피하는 방법으로 안내한다 [확인]. 하루 1회 health 요청이면 충분해 보인다 [추정]. 실행 위치는 Vercel Cron(vercel.json 수정 = 공유 파일, 추가만 하므로 위험은 낮음) 또는 외부 무료 cron 서비스(레포 변경 없음, PM 계정 필요) 중 하나다. 자동으로 계속 깨우는 것이 약관의 공정 사용 범위 안인지는 [미확인]이다.
- **멈췄을 때 깨지지 않게**: health가 `down`이면 랜딩은 "공유 서버에 연결할 수 없습니다. 연습(박대리)은 가능합니다"로 바꾸고 방 만들기만 막는다. 연습은 서버를 쓰지 않아 항상 된다.

| `SUPABASE_SERVICE_ROLE_KEY` | 서버 DB 읽기·쓰기, 초인종 발송 | 서버 전용 | /pae가 쓰므로 등록돼 있을 것 [추정] | 아니오 |
| `VERCEL_ENV` | 지표 오염 방지(`production`만 집계) | 서버 | Vercel이 자동으로 넣음 | 아니오 |

- **새 키 0개.** deploy.yaml의 env 드리프트 점검은 "위 4개 외에 `process.env`가 없음"을 확인하면 통과다.
- Vercel 토큰이 없어 등록 여부를 대시보드에서 직접 볼 수 없다. 대신 Supabase를 다시 켠 뒤 배포 후 검증에서 `/api/monthly-close/health`가 `db: ok`를 돌려주면 URL과 서비스 키가 모두 맞는 것이다. 초인종 키는 `transport` 이벤트로 확인한다.
- `.env.local`에는 Supabase 키가 없다 [확인]. 로컬 개발과 프리뷰 스크린샷은 MemoryStore로 한다. 운영 키를 로컬에 복사하라고 PM에게 요청하지 않는다.

## 12. 배포 전략

- **순서**: Supabase 다시 켜기(G0-1) → PM이 SQL 실행 → G0-2 → 로컬 게이트(type-check·클린 빌드·테스트, MemoryStore로 두 브라우저 한 판 완주) → 프리뷰 스크린샷 승인 → push(`git push mingame main`) → 배포 후 검증.
- **배포 후 검증(A-7 보강)**: ① 페이지에 고유 콘텐츠가 있는지 ② health `ok` ③ **테스트 표시를 단 연기 시험(smoke test)**: 비밀키 2개로 방 만들기 → 입장 → 배치 → 발사 1회 → 기권. 운영 Supabase 경로 전체를 확인하면서 지표에는 섞이지 않게 한다 ④ 익명 키로 `mc_rooms` 직접 조회 시 거부되는지 ⑤ /pae·/moira·/exam 회귀 확인.
- **공유 파일**: `layout.tsx`·`providers.tsx`·`globals.css`·`vercel.json`은 수정하지 않는다(깨우기를 Vercel Cron으로 고르면 그때 vercel.json 추가 변경을 따로 알린다).
- **롤백**: 앱은 Vercel "직전 배포 Promote" 또는 `git revert`로 되돌린다. DB는 `mc_` 테이블만 추가했으므로 되돌릴 필요가 없다. 지워야 하면 teardown SQL을 쓴다. 다른 앱 테이블에는 영향이 없다.

## 15. 다른 팀장과 맞출 것

**프론트팀장**
- 비밀키 생성과 보관(localStorage `mc:key`), 테스트 표시(`mc:test`), 헤더 전송. URL에는 넣지 않는다.
- sync 주기 표(§5)와 "숨기기 시작·해제 즉시 보고", `settleAt`·기한 도달 시 즉시 sync.
- 카운트다운은 `serverNow` 오프셋으로 표시. 판정은 서버 응답만 따른다.
- 방 페이지는 클라이언트 렌더링만(SSR 금지). 503이면 "점검 중 + 연습 가능" 화면.
- 박대리 연습은 엔진을 직접 import해서 서버 없이 돌린다(엔진은 브라우저에서도 쓰도록 순수 TS로 만든다).
- 판이 끝나면 `lines_shown`을 한 번 보낸다(문구 신고율 분모).

**디자인팀장**
- 서버를 기다리는 상태 문구: "계산 중..."(퀴즈 확정 대기, 액션 왕복), "다른 사용자 오프라인", "공유 서버에 연결할 수 없습니다".
- "같은 브라우저에서 다시 열어 주세요"(기기 변경 시 재입장 불가) 안내 문구.
- 없는 방과 꽉 찬 방은 같은 문구 "문서를 열 수 없습니다"로 보여 준다.

## 16. 별건 (월마감 범위 밖, 배포엔지니어·기획팀장 참고)
1. `supabase/pae-schema.sql`에 `room_players.ready` 칸이 없다. 실제 DB에는 있을 것으로 보이지만 [추정], 파일로 다시 만들면 /pae가 깨진다. 경우 B 전에 고쳐야 한다.
2. `pae-schema.sql`은 다시 실행하면 테이블을 지운다. 운영 중인 프로젝트에서는 실행하면 안 된다(경우 A에서는 실행할 필요 없음).
3. /pae는 `rooms`를 누구나 읽을 수 있어서(`using (true)`), 공개 키만 있으면 열린 방 번호 전체를 볼 수 있다 [확인]. 영향은 작지만 기록해 둔다.
4. /pae 방 만들기는 방 번호가 겹쳐도 다시 뽑지 않고 500을 낸다 [확인]. 확률은 낮다.
