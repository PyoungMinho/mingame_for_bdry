## 1. 결론 요약

PM 요청("AWS·Azure에서 자주 쓰는 것 4~5개를, 휴먼에러 없이 스스로 확인")을 **「문단속 5」**(가제)로 확정한다. 현관(MFA)·열쇠(자격증명)·창문(열린 포트)·창고(공개 저장소)·CCTV(감사 로그) 다섯 곳을 AWS와 Azure에서 점검하고, 항목마다 **위험·주의·이상 없음·확인 불가·해당 없음** 5상태와 고치는 법(먼저 확인 → 바꾸기 → 되돌리기)을 보여 준다. 창의팀의 콘셉트와 학습 경험(이름, 휴먼에러 3겹, 쌍둥이 카드, 가짜 회사, 고치는 법)에 비평팀의 신뢰 골격(증거 없으면 초록 없음, 호출 영수증, 조회 범위 패널, 파일 우선 수집기, 격리, 룰 18장 상한)을 얹는다.

이 도구가 약속하는 것은 "안전하다는 보증"이 아니라 **"어디까지 봤고 무엇을 못 봤는지 정직하게 말하는 것"**이다. 그래서 증거가 모자라면 초록 대신 회색이 나오고, 회색은 '직접 볼 목록'으로 사람에게 넘어간다. 키는 받지 않는다. 판정은 브라우저 안에서만 하고, 페이지는 외부 요청이 0인 자체 완결 HTML 한 장으로 만들며, 같은 파일이 오프라인판이 된다. 레포 루트 레이아웃이 모든 페이지에 광고 스크립트와 외부 폰트를 싣기 때문에 일반 `page.tsx`로는 이 약속을 지킬 수 없다 [확인: 레포]. 그래서 격리를 제품 요구사항(R-07·R-08)으로 고정하고, 서빙 방식은 팀장회의 스파이크 결과로 고른다.

출시는 AWS 베타를 먼저 하고, Azure는 PM 실계정 검증 뒤에 연다. 화면은 한국어로 시작하고 일본어는 v1.1로 미룬다(PM 확인 대기). PDF와의 관계는 이렇다. 1단계("읽기 → 기준 대조 → 리포트")를 실물로 구현하고, 2단계("MFA 미설정·오래된 토큰 찾기")는 현관·열쇠 문으로 덮으며, 3단계(규정 매핑)는 나중 범위로 둔다.

## 3. 제품 정의

### 3-1. 이름과 한 줄 약속
- 이름: **「문단속 5」**(가제). 일본어 「戸締まりチェック」(가제, 원어민 검수 전). "5"는 점검하는 곳의 수다. "5분"이라는 표현은 쓰지 않는다.
- 한 줄 약속: **"열쇠는 맡기지 않습니다. 읽기는 당신의 셸에서, 판정은 당신의 브라우저에서. 어디까지 봤고 무엇을 못 봤는지도 그대로 말합니다."**
- "문단속 끝!", "안전합니다", "OK" 같은 완료 카피는 쓰지 않는다 (§9).

### 3-2. 점검기 5종과 자주 쓰는 서비스 (PM 요청 대응)

### 3-3. 왜 5문을 유지하는가 (비평 P1-1 판정)
- 인정하는 부분: 실제 사고는 상당수가 설정값이 아니라 자격증명·협력사·취약점 경로로 일어난다 [확인: R2 양측].
- 그래도 유지하는 이유: 5문은 "자격증명이 털렸을 때 피해를 키우는 조건"을 본다. 개인정보위 2026-06-15 권고(임시 자격증명, IP·네트워크 제한, MFA, 최소 권한, 미사용 권한 회수) [확인: R2 창의]와 2021-09 제재(관리자 접근키 IP 미제한) [확인: R2 양측]가 현관·열쇠 규칙과 직접 맞닿는다. PDF 2단계("MFA 미설정 계정·오래된 토큰 찾기")와도 겹친다.
- 조정한 부분: 열쇠를 주력 문으로 키운다(4룰: 키 나이, 미사용, 관리자 키, 외부 계정 신뢰). '이 도구가 못 막는 경로' 패널을 둔다(노출된 키, 협력사 침해, 취약점 악용, 피싱 — 외부 가이드 링크). 사고와 문을 잇는 대응표는 검증된 사례로만 만든다 (§9-3).

### 3-7. 포지셔닝
- 입문 사다리의 첫 단으로 자리 잡는다. 5곳을 다 정리한 사용자에게는 Prowler, Defender for Cloud, CIS 벤치마크로 가는 **졸업 경로**를 안내한다. 수치를 앞세운 비교 문구는 쓰지 않는다.
- 차별점은 정직하게 말할 수 있는 것만 내세운다: 읽을 수 있는 작은 수집기(설치 0) / 확인 불가를 먼저 말하는 리포트 / 사용자가 직접 검증할 수 있는 무전송 / 한국어(곧 일본어)로 된 고치는 법과 되돌리기 / 오프라인 단일 HTML.
- 인정하는 부분: 기술 범위는 Prowler가 훨씬 넓고, Prowler도 CloudShell에서 돈다(pip/pipx 설치와 영어 출력이 필요) [확인: R2 비평].

예외 표시됨(파랑 띠: 사유·만료일) / 의도된 공개 후보 / 이름 힌트 / 본인 응답 / 베타(실계정 검증 전) / 체험 모드(가짜 데이터). 라벨은 상태를 바꾸지 않는다. 단 §2 #14의 정적 웹사이트 설정은 라벨이 아니라 룰 조건으로 판정에 반영한다.

### 5-3. 집계 규칙
- **항목 → 룰**: 위험이나 주의 항목이 하나라도 있으면 그중 가장 나쁜 상태를 룰 상태로 한다(양성은 부분 데이터에서도 믿는다). 하나도 없으면, 범위가 증명된 경우에만 이상 없음이나 해당 없음이 되고 그렇지 않으면 확인 불가가 된다.
- **룰 → 문**: 같은 규칙을 적용한다. 문이 초록이 되려면 그 문의 모든 룰이 이상 없음이거나 해당 없음이어야 한다.
- **리포트 전체**: 하나의 상태로 합치지 않는다. 분포만 보여 준다: "확인한 N개 항목 중 위험 a · 주의 b · 이상 없음 c · 확인 불가 d · 해당 없음 e". d가 0보다 크면 상단에 "아직 판단하지 못한 항목이 d개 있습니다"를 고정한다.
- **정렬**: 위험 → 주의 → 확인 불가 → 이상 없음 → 해당 없음. 처음에는 "먼저 볼 3개"만 펼친다. 순서는 룰 데이터의 `priority`를 따른다.

### 5-4. 불변식 (코드로 구현하고 QA 속성 테스트로 검증)

| ID | 불변식 |
|---|---|
| INV-1 | **fail-closed**: 모든 판정의 시작값은 확인 불가다. 증거로만 승격한다 |
| INV-2 | 빈 입력, 빈 파일, 파싱 실패에서는 이상 없음이 0개여야 한다 |
| INV-3 | 증거를 지우는 변이(필드 삭제, AccessDenied 주입, 잘림, 리전·구독 제거, 스키마 버전 변경)는 어떤 항목도 이상 없음으로 만들 수 없다 (vitest + fast-check 속성 테스트 — 둘 다 레포에 있음 [확인: package.json]) |
| INV-4 | **비대칭 원칙**: 위험·주의는 부분 데이터에서도 유지된다. 반면 "없음"(→ 이상 없음)은 범위가 증명될 때만 인정한다. Resource Graph CSV 출처로는 룰 수준의 '없음'을 만들 수 없다 |
| INV-5 | **모수 0**: 목록이 비면 이상 없음을 줄 수 없다. 목록이 완결됐다는 증명이 있으면 해당 없음, 없으면 확인 불가다 |
| INV-6 | '설정 없음' 응답(예: `NoSuchPublicAccessBlockConfiguration`)은 유효한 답이다. `AccessDenied`는 답이 아니다 |
| INV-7 | 같은 계열 호출이 다른 리소스에서는 성공했는데 특정 리소스에서만 거부되면 주의로 올린다 (Trusted Advisor 2025 우회 패턴 [확인: R2 양측]) |
| INV-8 | 본인 응답과 예외 표시는 상태를 바꾸지 않는다 |
| INV-9 | 판정은 순수 함수다. 나이·경과일은 브라우저의 현재 시각이 아니라 **파일의 수집 시각** 기준으로 계산하므로, 같은 파일은 언제 열어도 같은 결과가 나온다. 현재 시각과의 차이는 배너로만 알린다(24시간 초과 시 "오래된 사진", 7일 초과 시 강조 배너. 기준값은 파라미터) |
| INV-10 | 수집기 버전·스키마가 맞지 않거나 필수 키가 빠지면 해당 영역 전체를 확인 불가로 하고 배너를 띄운다. JSON 안의 수집기 해시는 버전 확인용일 뿐 보안 증거가 아니다 |

### 5-5. 리포트 첫 화면 (접을 수 없는 영역)
- **신원**: 클라우드, 계정 별칭 + ID 끝 4자리(또는 테넌트·구독 끝 4자리), 실행 주체 유형(역할/사용자)
- **범위**: AWS 리전 "확인 N / 활성 M"(빠진 리전 목록), Azure 구독 "조회 N / 보이는 M"
- **수집**: 시각(UTC와 한국 시간), 수집기 버전, 호출 성공·거부·오류·잘림 수, 자격증명 리포트 생성 시각(있을 때)
- **권한**: 거부된 호출 목록 + "이 권한이 있으면 확인 불가 K개를 풀 수 있습니다"
- **못 보는 것(고정)**: 코드 저장소·로그에 노출된 키, 발급된 SAS·OAuth 토큰, 다른 계정·조직·구독, 방치된 테스트 환경이 있는지 여부, 앱 취약점, ID 공급자(Identity Center·외부 IdP) 쪽 MFA, 리소스 기반 정책을 통한 외부 공유
- **분포 요약**, "아직 판단하지 못한 항목 d개" 배너, 면책 1줄 (§9-2)
- **직접 볼 목록**(인쇄 가능): 확인 불가 항목 + 가이드 카드 + 범위 밖 고지

### 6-2. 룰 상세

**AWS-MFA-1 루트 계정 문단속** · 현관 · 최고 위험
- 위험: 루트 액세스 키가 활성(`access_key_1/2_active`=TRUE)이거나, 루트에 비밀번호가 있는데(`password_enabled`=TRUE) `mfa_active`=FALSE
- 주의: 최근 90일 안에 루트로 콘솔에 로그인함(일상 사용 의심. "루트로 일상 작업을 하나요?")
- 이상 없음: 루트 행 존재 + 비밀번호 있음 + MFA 켜짐 + 루트 키 0개 + 최근 90일 루트 로그인 없음
- 해당 없음: `password_enabled`=FALSE이고 키 0개 → "루트 자격증명 없음(확인됨)". Organizations 신규 멤버 계정은 기본으로 루트 자격증명이 없고, 중앙 루트 관리로 삭제할 수도 있다 [확인: AWS IAM 문서]. 이 경우를 위험으로 오탐하지 않는다
- 확인 불가: 리포트 거부·부재, 루트 행 없음, 열 누락, `password_enabled` 값이 TRUE/FALSE가 아님(스크립트 경로의 `get-account-summary`로 보완)
- 데이터: 자격증명 리포트의 루트 행. 키 관련 열은 루트에도 적용된다 [확인: AWS IAM 문서]. 스크립트 경로는 `iam get-account-summary`로 교차 확인
- 못 보는 것: MFA 장치 종류, 루트 이메일·연락처 보안, 관리 계정의 루트(멤버 계정에서 점검할 때)

**AWS-MFA-2 콘솔 사용자 MFA** · 현관 · 최고 위험
- 위험: 콘솔 비밀번호가 있는데 MFA가 없는 사용자가 1명 이상
- 이상 없음: 콘솔 비밀번호 사용자가 1명 이상이고 전원 MFA 켜짐
- 해당 없음: 콘솔 비밀번호 사용자 0명(확인됨). 이때 '직접 볼 목록'에 "Identity Center·외부 IdP를 쓴다면 그쪽 MFA를 직접 확인하세요"를 자동으로 넣는다
- 확인 불가: 리포트 거부, 열 누락
- 데이터: 리포트의 IAM 사용자 행. 리포트는 최대 4시간 캐시되므로 [확인: AWS IAM 문서], 스크립트 경로에서는 지적된 사용자를 실시간 MFA 조회로 교차 확인한다(방식은 API설계자가 정한다)
- 못 보는 것: Identity Center·외부 IdP 사용자, MFA 강제 정책(`aws:MultiFactorAuthPresent` 조건), 서비스 전용 자격증명

**AWS-KEY-1 오래된 액세스 키** · 열쇠 · 최고 주의
- 주의: 활성 키를 만들거나 회전한 지 90일이 넘음. 안내 문구: "장기 키 대신 임시 자격증명을 권장합니다"(개인정보위 2026-06 권고 [확인: R2 창의])
- 이상 없음: 모든 활성 키가 90일 이내
- 해당 없음: 활성 키 0개(확인됨)
- 확인 불가: 리포트 거부, 열 누락. CSV에서 `additional_credentials_info` 칸에 값이 있으면 추가 키는 확인 불가로 두고 스크립트 경로를 안내한다(리포트에는 사용자당 처음 2개 키만 들어간다 [확인: AWS IAM 문서])
- 데이터: 리포트의 `access_key_N_active`, `access_key_N_last_rotated` / 스크립트 `iam list-access-keys`. 루트 키는 AWS-MFA-1에서 다루므로 여기서 중복 판정하지 않는다
- 못 보는 것: 키가 어디에 저장되거나 노출됐는지(GitHub 등), 서비스 전용 자격증명(CodeCommit 비밀번호, Bedrock 장기 API 키 등 [확인: AWS IAM 문서])

**AWS-KEY-2 쓰지 않는 자격증명** · 열쇠 · 최고 주의
- 주의: 활성 키를 마지막으로 쓴 지 90일이 넘었거나 한 번도 쓰지 않음(만든 지 7일이 지난 경우만). 콘솔 비밀번호도 같은 기준
- 이상 없음: 활성 자격증명을 전부 90일 안에 사용
- 해당 없음: 활성 자격증명 0
- 확인 불가: 리포트 거부, 열 누락
- 데이터: 리포트의 `access_key_N_last_used_date`, `password_last_used`, `user_creation_time`
- 못 보는 것: 역할(Role)의 미사용, 권한 단위의 미사용(나중: Access Analyzer)

**AWS-KEY-3 관리자 열쇠 출입 제한 안내** · 열쇠 · 주의 전용(초록 없음)
- 주의: 관리자급 관리형 정책이 직접 또는 그룹으로 붙은 IAM 사용자에게 활성 액세스 키가 있음. 안내 문구: "관리자 키는 IP 제한이나 임시 자격증명 전환을 권장합니다. 이 도구는 정책 조건(IP 제한)을 해석하지 않습니다." 근거: 2021 개인정보위 제재, 관리자 접근키 IP 미제한 [확인: R2 양측]
- 이상 없음: 이 룰은 이상 없음을 주지 않는다
- 해당 없음: 그런 사용자 0명(목록 완결)
- 확인 불가: 목록 거부, 잘림
- 데이터(스크립트 전용): `iam list-users`, `list-attached-user-policies`, `list-groups-for-user`, `list-attached-group-policies`. 정책 ARN만 수집한다
- 못 보는 것: IP 조건의 유무와 적정성, 인라인·고객 관리형 정책에 든 관리자급 권한, 권한 경계·SCP

**AWS-KEY-4 남에게 맡긴 열쇠(외부 계정 신뢰)** · 열쇠 · 최고 위험
- 위험: 신뢰 정책의 Principal이 `*`(또는 `"AWS": "*"`)이고 Condition이 없음
- 주의: 자기 계정이 아닌 AWS 계정 ID를 신뢰하면서 `sts:ExternalId` 조건이 없음. 안내 문구: "협력사·외부 계정에 맡긴 열쇠입니다. 의도한 것인지 확인하세요(같은 조직의 계정이면 예외로 표시)". Principal이 `*`이지만 Condition이 있는 경우도 주의
- 이상 없음: `list-roles` 성공 + 페이지 완결 + 외부 주체 0(서비스 주체, 자기 계정, 서비스 연결 역할은 제외)
- 해당 없음: 사용자가 만든 역할 0
- 확인 불가: 거부, 잘림
- 데이터(스크립트): `iam list-roles` 응답의 신뢰 정책에서 Principal 값과 Condition 키 이름만 뽑는다. 정책 전문은 수집하지 않는다
- 못 보는 것: 리소스 기반 정책(S3·KMS 등)을 통한 외부 공유, 같은 조직 소속인지 여부, SCP, Identity Center 권한 세트, OIDC·SAML 신뢰 조건의 적정성(GitHub Actions OIDC 점검은 나중 후보)

**AWS-NET-1 인터넷에 열린 관리·DB 포트** · 창문 · 최고 위험
- 위험: `0.0.0.0/0`이나 `::/0`에 위험 포트 또는 전체 포트·프로토콜을 연 보안 그룹이, 공인 IP가 있는 ENI에 연결돼 있음
- 주의: 같은 규칙이 있지만 연결된 ENI가 없거나 공인 IP를 확인할 수 없음("무장은 됐지만 연결 안 됨"). 위험 목록 밖의 포트가 인터넷 전체에 열림(80·443 제외)
- 이상 없음: 활성 리전을 전부 조회하는 데 성공했고 해당 규칙이 0개
- 확인 불가: 리전 일부가 거부·오류·누락이면 그 리전은 회색이고 룰 수준의 '없음'은 줄 수 없다. 다른 리전에서 찾은 위험은 그대로 유지한다
- 데이터(스크립트): `ec2 describe-regions`, 리전별 `describe-security-groups`, `describe-network-interfaces`
- 못 보는 것: NACL, Network Firewall, WAF, 로드밸런서를 거친 노출, 프리픽스 리스트 내용, 그 포트에서 실제로 서비스가 응답하는지(외부 접속 시도는 하지 않는다)

**AWS-STO-1 계정 전체 퍼블릭 액세스 차단** · 창고 · 최고 주의
- 주의: 4항목 중 하나라도 false이거나 '설정 없음'(`NoSuchPublicAccessBlockConfiguration`, 유효한 답으로 취급)
- 이상 없음: 4항목 모두 true
- 확인 불가: 거부, 오류
- 데이터: `sts get-caller-identity` → `s3control get-public-access-block`
- 못 보는 것: 액세스 포인트 설정, 조직 수준 정책, 다른 계정

**AWS-STO-2 공개된 버킷** · 창고 · 최고 위험
- 위험: 공개가 확인됨(`get-bucket-policy-status`의 IsPublic=true이거나 ACL이 AllUsers·AuthenticatedUsers에 권한을 줌) + 계정·버킷 차단 설정이 이를 막지 않음 + 정적 웹사이트 호스팅이 아님
- 주의: ① 정적 웹사이트 호스팅 버킷이 공개됨 → '의도된 공개 후보' 라벨 + "공개되면 안 되는 파일이 없나요?" ② 공개는 아니지만 계정·버킷 차단이 모두 꺼진 "공개 가능 상태", 또는 ACL이 켜져 있고 IgnorePublicAcls가 꺼져 객체 단위 공개 가능성이 있음 ③ 다른 버킷 조회는 성공했는데 이 버킷의 점검 조회만 거부됨("점검을 막는 정책일 수 있습니다". Trusted Advisor 2025 우회 패턴 [확인: R2 양측])
- 이상 없음: 계정 차단 4항목이 true(버킷 전체에 적용), 또는 버킷 차단 4항목이 true, 또는 IsPublic=false이면서 ACL 공개 부여가 없음. 셋 다 버킷 목록이 완결됐다는 전제
- 해당 없음: 버킷 0개
- 확인 불가: `list-buckets` 거부, 버킷별 조회 오류(③ 제외)
- 이름 힌트(public·static·assets·cdn)는 라벨만 붙이고 판정은 바꾸지 않는다. 생성 시기도 확인 순서를 정하는 힌트일 뿐이다(2023-04부터 신규 버킷만 기본 차단 [확인: R2 양측])
- 데이터(스크립트): `s3api list-buckets`, 버킷별 `get-bucket-location`, `get-public-access-block`, `get-bucket-policy-status`, `get-bucket-acl`(공개 부여만 뽑음), `get-bucket-ownership-controls`, `get-bucket-website`
- 못 보는 것: 객체 단위 ACL, 사전 서명 URL, 액세스 포인트 정책, CloudFront를 거친 공개, 특정 외부 계정에만 열린 정책(정책 전문을 수집하지 않음), 버킷 안 파일의 민감도

**AWS-LOG-1 CloudTrail 장기 기록** · CCTV · 최고 주의
- 주의: trail 없음 / 다중 리전 아님 / 기록 중지(IsLogging=false — 의도한 것인지 확인) / 관리 이벤트에 쓰기 미포함 / 로그 파일 검증 꺼짐
- 문구 규칙: "trail 없음 = 로그 없음"이라고 쓰지 않는다. 대신 "최근 90일 관리 이벤트는 기본으로 남지만 그 뒤로는 사라지고, 데이터 이벤트는 남지 않습니다"라고 쓴다 [확인: R2 비평]
- 이상 없음: 다중 리전 + 기록 중 + 관리 이벤트(최소 쓰기) + 로그 파일 검증
- 확인 불가: 거부, 오류, 조직 trail의 상태를 조회할 수 없음
- 데이터(스크립트): `cloudtrail describe-trails`, `get-trail-status`, `get-event-selectors`
- 못 보는 것: 데이터 이벤트 범위, 로그 보관 기간과 버킷 수명주기, 알림·모니터링 여부

**AZ-MFA-G Entra MFA 포털 확인** · 현관 · 가이드 카드(항상 확인 불가)
- 자동으로 판정하지 않는다. 포털에서 확인할 3단계를 안내한다: ① 보안 기본값(Security defaults)을 쓰는지, 또는 ② 모든 사용자에게 MFA를 요구하는 조건부 액세스 정책이 있는지 ③ 관리자 역할에 MFA가 걸려 있는지
- 사용자가 체크하면 '본인 응답' 라벨로 리포트와 인쇄본에 기록한다. 상태는 확인 불가 그대로다
- 화면에 비대칭을 그대로 드러낸다: "AWS 현관은 파일로 판정하고, Azure 현관은 직접 확인합니다"

**AZ-MFA-1 Entra 사용자 등록 현황** · 현관 · 조건부 편입, 양성 전용(초록 없음)
- 편입 조건: PM 검증에서 포털 CSV 다운로드, 열 구성, 라이선스 요건이 모두 확인될 것
- 위험: 관리자 역할 사용자가 MFA 가능 상태가 아님(해당 열이 있을 때) / 주의: 일반 사용자 미등록
- 그 밖의 경우: 확인 불가 + "등록 여부만 봤습니다. 강제 여부(보안 기본값·조건부 액세스)는 가이드 카드에서 확인하세요". 등록 ≠ 강제이고, 최대 36시간 지연되며 비활성 사용자는 빠진다 [확인: R2 창의]

**AZ-KEY-1 스토리지 공유 키 회전** · 열쇠 · 최고 주의
- 주의: 공유 키 허용(`allowSharedKeyAccess`가 true 또는 null) + 두 키 중 하나라도 90일 넘게 회전하지 않았거나 `keyCreationTime` 기록이 없음
- 이상 없음: `allowSharedKeyAccess`=false(Entra 인증만 사용), 또는 공유 키를 허용하지만 두 키 모두 90일 안에 회전
- 확인 불가: 계정 목록 거부, 속성이나 열 누락. CSV 출처면 개별 계정만 판정하고 룰 수준의 '없음'은 주지 않는다
- 안내: 키 만료 정책(`keyPolicy`)과 SAS 만료 정책 설정을 권장한다
- 데이터: `az storage account list` 또는 Resource Graph CSV의 `allowSharedKeyAccess`, `keyCreationTime` [확인: MS 문서], `keyPolicy` [확인: MS API 참조], `sasPolicy`. **키 값을 읽는 명령은 절대 쓰지 않는다** (C-03)
- 못 보는 것: 이미 발급된 SAS 토큰(목록으로 볼 수 없음 — 고정 고지), 키를 어디서 쓰는지와 노출 여부, 앱 등록 시크릿·인증서(Graph가 필요해 나중)

**AZ-NET-1 인터넷에 열린 관리·DB 포트(NSG)** · 창문 · 최고 위험
- 위험: Inbound Allow + 출발지 `*`·`Internet`·`0.0.0.0/0`·`Any` + 위험 포트나 전체 포트 + 같은 범위를 막는 더 높은 우선순위 Deny 없음(단순 평가) + 공인 IP가 있는 NIC나, 그런 NIC가 있는 서브넷에 연결됨
- 주의: 같은 규칙이 있지만 연결·공인 IP를 확인할 수 없거나 연결돼 있지 않음. ASG나 서비스 태그가 섞여 단순 평가가 불확실함
- 이상 없음: 스크립트 경로로 조회한 구독이 전부 성공했고 해당 규칙이 0개
- 확인 불가: 구독 일부 실패, CSV 경로에서 나온 '없음'
- 데이터: `az network nsg list`, `nic list`, `public-ip list` 또는 Resource Graph CSV(규칙을 펼친 공개 쿼리)
- 못 보는 것: Azure Firewall, ASG 멤버십, Bastion·JIT, 로드밸런서 인바운드 NAT, 실제 응답 여부

**AZ-STO-1 계정의 익명 공개 허용** · 창고 · 최고 주의
- 주의: `allowBlobPublicAccess`가 true이거나, null 또는 속성 없음("미설정 — 공개 차단 아님". MS 공식 스크립트도 null을 차단 아님으로 처리한다 [확인: R2 양측])
- 이상 없음: false
- 확인 불가: 계정 목록 거부, CSV에 열 없음
- 계정 생성 시기는 쓰지 않는다. "2023-08 기본값 변경"은 [2차]·[미확인]이라 관측된 속성만 근거로 쓴다
- 못 보는 것: 정적 웹사이트(`$web`) 공개(이 설정과 무관하다 [확인: R2 양측]), SAS

**AZ-STO-2 공개된 컨테이너** · 창고 · 최고 위험
- 위험: 계정의 `allowBlobPublicAccess`가 false가 아님 + 컨테이너 `publicAccess`가 Blob이나 Container + 컨테이너가 `$web`이 아님
- 주의: `$web`이 있음(정적 웹사이트 — 의도된 공개 후보). 다른 계정은 조회됐는데 이 계정만 거부됨
- 이상 없음: 계정 `allowBlobPublicAccess`=false(컨테이너 설정을 무력화함), 또는 컨테이너 목록이 완결됐고 전부 None
- 해당 없음: 컨테이너 0개
- 확인 불가: 목록 거부, 오류
- 데이터(스크립트): 계정별 `az storage container-rm list`(관리 평면). 구독 Reader로 되는지는 [미확인]
- 못 보는 것: SAS, 익명 요청이 실제로 오는지(고치는 법의 '먼저 확인' 단계에서 메트릭으로 안내), 파일 내용

**AZ-LOG-1 활동 로그 장기 보관** · CCTV · 최고 주의
- 주의: 구독 진단 설정이 없음 → "활동 로그는 항상 수집되지만 90일 뒤 사라집니다" [확인: R2 비평]. Administrative·Security 범주가 빠짐
- 이상 없음: Administrative·Security 범주를 Log Analytics나 Storage로 내보내는 설정이 있음
- 확인 불가: 거부, 오류
- 데이터(스크립트): `az monitor diagnostic-settings subscription list`
- '활동 로그 켜짐/꺼짐' 항목은 만들지 않는다. 활동 로그는 항상 수집되고 끌 수 없다 [확인: R2 비평]
- 못 보는 것: 내보낸 곳의 보관 기간, 알림 규칙, Entra 로그인·감사 로그(테넌트 진단 설정)

**AZ-LOG-2 Blob 접근 기록** · CCTV · 최고 주의
- 주의: 스토리지 계정의 Blob 서비스에 진단 설정이 없거나, StorageRead·StorageWrite·StorageDelete가 빠짐 → "누가 파일을 읽었는지 남지 않습니다"(리소스 로그는 기본으로 수집되지 않는다 [확인: R2 비평])
- 이상 없음: 세 범주 모두 수집
- 해당 없음: 스토리지 계정 0개
- 확인 불가: 거부, 오류
- 데이터(스크립트): 계정별 `az monitor diagnostic-settings list --resource <계정>/blobServices/default`
- 못 보는 것: 보관 기간, 실제로 모니터링하는지 여부

### 6-3. 룰 공통 규격
- **룰 데이터**(zod 스키마로 강제): `id`, `cloud`, `door`, 제목·설명(i18n 키), `maxState`, `allowsGreen`, `params`, `requiredEvidence`, `sources`(호출·CSV 열), `permissions`, `cannotSee[]`, `falsePositiveScenarios[]`, `fix{observe, change{docUrl, property, cliExample(자리표시자 포함)}, revert, impact(낮음·중간·높음), prodImpact}`, `basis[]`(근거 링크), `lastVerified`, `priority`, `incidentRef?`
- 판정 로직은 룰별 순수 함수(TS)로, 문구·기준값은 데이터로 둔다. 둘 다 번들에 들어가므로 룰을 바꾸면 새 릴리스가 된다.
- **룰 출시 기준(1장마다)**:
  1. 데이터 소스와 필요 권한 문서화
  2. 6케이스 픽스처: 성공-통과, 성공-위반, 거부, 잘림, 필드 부재, 버전 불일치
  3. 가짜 회사 정답지에 반영
  4. 고치는 법 3단계 + 영향도 + `lastVerified`
  5. 오탐 시나리오와 못 보는 것 기록
  6. PM 실계정 검증에서 정답지 대비 오탐률 10% 미만 목표 (Google Tricorder 기준 [확인: R2 비평])
- **룰 목록 보기**: 페이지 안에서 모든 룰의 조건, 근거, 못 보는 것을 사람이 읽을 수 있게 보여 준다.

| ② 수집기 파일 (권장 완전판) | `cloudcheck-aws.sh` 또는 `cloudcheck-azure.sh`를 내려받아 읽는다 → CloudShell에 업로드(또는 로컬 CLI) → `sha256sum`으로 해시 대조 → `bash`로 실행 → JSON 1개 생성 → 내려받아 페이지에 드롭 | 가이드 카드를 뺀 전부 | 업로드에는 `cloudshell:GetFileUploadUrls`가 필요하고, VPC 환경에서는 안 되며, 조직이 막을 수 있다 [확인: R2 비평]. | ③ 결과 붙여넣기 | 다운로드가 막히면 터미널에 출력된 JSON을 복사해 페이지 입력칸에 붙인다(셸 → 페이지 방향만) | ②와 같음 | 큰 출력은 복사하다 깨질 수 있다. 파싱에 실패하면 확인 불가 배너를 띄운다. 문 단위 출력 옵션을 제공 |

- 셸에 붙여넣는 명령 블록은 MVP에서 제공하지 않는다. 사용자가 셸에 직접 입력하는 명령은 `sha256sum <파일>`과 `bash <파일>` 두 줄뿐이고, 원클릭 복사 버튼 없이 "직접 입력하세요"라고 안내한다. `curl … | bash` 형태는 영구 금지다.

### 7-3. 사용자 실행 흐름 (1순위, AWS 예시)
1. `/cloudcheck` 접속 → 클라우드 선택(AWS) → 경로 선택(① CSV만 / ② 수집기)
2. ②를 고르면 스크립트 원문(문별로 접힘), 예상 발자국 표, 해시(페이지·저장소·PDF)를 보여 준다 → 파일 내려받기
3. CloudShell 열기 → 업로드 → `sha256sum cloudcheck-aws.sh` 직접 입력 → 해시 대조 → `bash cloudcheck-aws.sh` → 계정 확인(Enter) → 진행 → JSON 생성
4. CloudShell에서 파일을 내려받아(막히면 ③ 붙여넣기) 페이지에 드롭
5. 리포트: 조회 범위 패널 → 분포 → 먼저 볼 3개 → 문별 카드 → 직접 볼 목록
6. 고치기(별도 화면) → 다시 수집 → Before/After

### 7-4. 수집 계약 초안 (팀장회의에서 v1 확정)

```json
{
  "schema": "cloudcheck.collect/1",
  "collector": { "name": "cloudcheck-aws", "version": "1.0.0" },
  "cloud": "aws",
  "collectedAt": "2026-10-19T03:12:00Z",
  "identity": { "accountId": "<전체 — 화면·내보내기에서 마스킹>", "alias": "acme-dev", "principalType": "assumed-role" },
  "scope": {
    "regionsEnabled": ["ap-northeast-2", "us-east-1"],
    "regionsSucceeded": ["ap-northeast-2"],
    "regionsFailed": [{ "region": "us-east-1", "receipt": "r-031" }]
  },
  "receipts": [
    { "id": "r-001", "call": "iam:GetCredentialReport", "region": "global",
      "result": "ok", "count": 12, "errorCode": null, "at": "2026-10-19T03:12:04Z" }
  ],
  "data": {
    "credentialReport": { "receipt": "r-001", "generatedAt": "…", "rows": ["허용 목록 열만"] },
    "securityGroups": [{ "region": "ap-northeast-2", "receipt": "r-010", "items": [] }]
  }
}
```

계약 규칙:
- 모든 데이터 묶음은 영수증 id를 참조한다. 영수증이 없는 데이터는 판정에 쓰지 않는다.
- `identity.accountId`는 전체 값을 보존한다. 외부 계정 판정(AWS-KEY-4)과 Before/After 계정 일치 확인에 필요하기 때문이다. 마스킹은 표시·내보내기 단계에서 한다.
- CSV 입력은 페이지가 같은 내부 모델로 정규화한다. `source`는 `csv-credential-report` 또는 `csv-resource-graph`이고, 범위 증명 여부(`scopeProven`)를 표기한다. 자격증명 리포트는 계정의 모든 IAM 사용자를 담으므로 true [확인: AWS IAM 문서], Resource Graph는 false.
- 스키마 버전은 semver를 따른다. 판정기는 지원 버전 목록을 갖고, 맞지 않으면 해당 영역을 확인 불가로 처리한다.
- 두 번째 계약인 **판정 결과 모델**(엔진 → UI)에는 신원, 범위, 분포, 문·룰·항목 상태, 사유 코드, 증거 참조, 라벨, 직접 볼 목록이 들어간다. 이 두 계약이 서야 수집기(백엔드), 엔진, UI(프론트), 픽스처(DB·QA)가 병렬로 진행된다.

### 7-5. 예상 발자국
- 수집기가 부르는 API 목록은 린터가 스크립트에서 뽑아 표로 만들고, 페이지와 저장소에 공개한다.
- AWS 대조 실습(선택): CloudTrail 이벤트 기록은 조회 이벤트도 남기지만 콘솔 기본 필터("읽기 전용: false")가 이를 숨기고, 기록은 리전별로 나뉜다 [2차: AWS CloudTrail 문서 검색 요약]. 필터를 풀고 사용자 이름으로 걸러 대조하도록 안내한다. PM 검증 뒤 베타 표시를 뗀다.
- Azure: 활동 로그는 보통 읽기 작업을 기록하지 않아 대조할 수 없다 [확인: R2 비평]. 이 사실을 정직하게 알린다.
- "쓰기 0건"은 약속하지 않는다(`GenerateCredentialReport`가 CloudTrail에서 읽기로 기록되는지 [미확인]). 약속하는 문구는 "예상 목록과 일치하는지 직접 확인할 수 있습니다"까지다.

### 8-2. 헤더 기준값 (①안 기준. 최종 문자열은 프론트팀장이 정한다)

```
Content-Security-Policy:
  default-src 'none'; script-src 'sha256-<번들 해시>'; style-src 'sha256-<CSS 해시>';
  img-src data: blob:; font-src data:; connect-src 'none'; form-action 'none';
  frame-src 'none'; frame-ancestors 'none'; base-uri 'none'; object-src 'none';
  worker-src 'none'; manifest-src 'none'
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Resource-Policy: same-origin
Referrer-Policy: no-referrer
X-Content-Type-Options: nosniff
Permissions-Policy: camera=(), microphone=(), geolocation=()
X-Robots-Tag: noindex          ← 베타 기간에만 (sitemap은 라우트를 수동 나열하므로 손대지 않으면 미등록 [확인: src/app/sitemap.ts])
```

- `img-src`에 `'self'`를 넣지 않는다. 같은 origin에 다른 앱의 API 경로(`/api/*`)가 있어서, 이미지 요청으로 데이터를 내보낼 길을 남기지 않기 위해서다.
- 폰트는 시스템 폰트 또는 data: 인라인만 쓴다. 외부 폰트는 금지.
- `require-trusted-types-for 'script'` 추가는 프론트팀장이 호환성을 확인한 뒤 결정한다.
- 프리뷰 배포에는 Vercel 툴바 스크립트가 주입돼 CSP 위반 로그가 보일 수 있다 [미확인]. 헤더와 외부 요청은 프로덕션 기준으로 판정한다.

Route Handler에는 루트 레이아웃이 적용되지 않는다 [일반 지식, S1에서 확인] | 충족 | 수정 없음 | 번들 생성 파이프라인이 필요하다. 정적 Route Handler의 응답 헤더가 Vercel에서 유지되는지는 [미확인]. 안 되면 `dynamic = 'force-dynamic'`으로 함수가 응답하게 한다(헤더는 확실히 유지되지만 요청마다 함수 실행) [일반 지식] | S1 스파이크 통과 |

| ③ | `vercel.json` 경로 헤더 + 일반 `page.tsx` | 미달. `'unsafe-inline'`이 필요하고 [확인: R2 양측], 루트 레이아웃의 광고·폰트 태그가 '부재'가 아니라 '차단'으로 처리돼 콘솔에 위반 로그가 쌓인다. 그러면 '직접 확인하기' 시험이 흐려진다 | 충족 | `vercel.json` 수정(문법 오류 하나가 전 앱 배포를 깬다) | — | 공개 출시에는 쓰지 않는다. 긴급 임시 조치로만 |

- `page.tsx`와 `route.ts`는 같은 세그먼트에 둘 수 없다 [일반 지식]. ①안이면 `/cloudcheck`에 page를 두지 않는다.

### 8-4. ①안의 남은 위험과 대응
- 같은 origin의 다른 앱이 루트 범위 Service Worker를 등록하면 `/cloudcheck` 요청을 가로챌 수 있다. 지금은 등록 코드가 없다 [확인: 레포]. 배포 게이트에 "src 전체에 `serviceWorker.register` 없음" 검사를 넣자고 제안한다 (T7).
- 같은 origin의 저장소(localStorage 등)는 쓰지 않으므로 공유 문제가 없다 (R-06). 다른 창이 이 페이지를 스크립트로 조작하는 경로는 COOP same-origin과 `frame-ancestors 'none'`으로 막는다 [일반 지식].
- 도메인 신뢰: `*.vercel.app`은 유사 주소로 사칭하기 쉽고, 지금 주소는 게임·심리테스트와 같다. 그래서 PDF에 정식 주소와 해시를 인쇄하는 것(독립 채널)이 핵심이다. 브랜드 분리(②)는 PDF 공개 전에 PM이 결정한다.
- 배포 저장소 `mingame_for_bdry`는 **공개 저장소**다 [확인: gh]. 소스 공개는 이미 성립한다. 대신 (1) PM 실계정 골든 파일은 완전히 마스킹한 뒤 리뷰를 거쳐서만 커밋하고 (2) PDF에 인쇄할 저장소는 수집기 전용 공개 저장소가 더 깔끔하다(PM 결정, Q7).

## 10. 고치는 법, 예외, 재점검

**고치는 법 카드** (룰 데이터의 `fix`)
1. **먼저 확인**(영향 관찰). 예: Azure 익명 접근을 막기 전에 익명 요청 메트릭을 본다(MS 문서도 관찰을 권고한다 [확인: R2 양측]). S3 차단을 켜기 전에 정적 사이트나 외부에서 의존하는 곳이 있는지 본다. 공유 키를 막기 전에 키로 접속하는 앱을 찾는다. 키를 폐기하기 전에 마지막 사용 서비스·리전 열로 사용처를 확인한다 [확인: AWS IAM 문서].
2. **바꾸기**. 공식 문서 딥링크와 함께, 바뀌기 쉬운 콘솔 메뉴 이름 대신 **속성명**을 쓴다. CLI 예시에는 `<버킷이름>` 같은 자리표시자를 넣어 그대로 붙여 넣어서는 실행되지 않게 한다.
3. **되돌리기**. 되돌리는 방법을 1줄로 적는다.
- 영향도(낮음·중간·높음), "운영 영향 가능" 라벨, 근거 링크, `lastVerified`를 붙인다. 180일이 지나면 '오래된 안내' 배너를 띄운다.
- 쓰기 명령은 수집 화면에 나오지 않는다. 고치기는 별도 화면에서 한다.
- 키가 노출된 경우의 대응은 "발견 즉시 폐기·교체" 런북 링크로 안내한다.

**예외**
- 형식은 `cloudcheck-exceptions.json` `{version, entries:[{ruleId, resource, reason, until, createdAt}]}`이다.
- 사유와 만료일은 필수이고, 최대 기간은 파라미터로 둔다. 만료되면 자동으로 해제된다.
- 불러온 예외의 대상이 현재 파일에 없으면 '대상 없음'으로 표시한다. 예외는 상태를 바꾸지 않는다 (INV-8).

**재점검 (Before/After)**
- 수집 파일 두 개를 비교한다. 계정이나 클라우드가 다르면 "다른 계정의 파일입니다"라며 비교를 거부한다(점검자 휴먼에러 방지).
- 룰별 상태 변화(예: 위험 3→1)를 보여 준다.
- 두 파일의 자격증명 리포트 생성 시각이 같으면 "리포트가 최대 4시간 캐시되므로 아직 반영되지 않았을 수 있습니다" 배너를 띄운다 [확인: AWS IAM 문서].

### 16-2. PM이 직접 할 일 (우리 팀은 실계정에 접근할 수 없다)

**AWS**
1. CloudShell이 뜨는지, 파일 업로드·다운로드가 되는지 확인하고 jq와 aws CLI 버전을 기록한다.
2. IAM 콘솔에서 자격증명 보고서 CSV를 내려받아, 파일명이나 내용에 생성 시각이 들어 있는지 본다 [미확인].
3. 수집기를 실행한다. 가능하면 SecurityAudit 역할로 한 번, 본인 권한으로 한 번. 막힌 호출과 걸린 시간을 기록한다.
4. V1용 "무장은 됐지만 연결 안 된" 결함을 심는다(체크리스트와 철거 목록은 QA가 준다). 예: 어떤 ENI에도 안 붙은 보안 그룹에 `0.0.0.0/0:22`, 빈 버킷의 차단 끄기, 오래 안 쓴 테스트 키. 실제 노출(공인 IP + 열린 22번)은 만들지 않는다.
5. CloudTrail 이벤트 기록에서 '읽기 전용' 필터를 풀고 수집기 실행 흔적을 대조한다(발자국 실습 검증).
6. 리포트 판정을 정답지와 대조하고, 오탐과 확인 불가 사유를 기록한다.
7. 수집 파일의 마스킹 사본을 저장해 골든 파일로 넘긴다. 공개 저장소에 들어가므로 마스킹을 한 번 더 확인한다.
8. 계정이 Organizations에 속하는지 확인한다(루트 자격증명 없는 멤버 계정의 판정 확인용).

**Azure**
1. Cloud Shell(스토리지 없는 임시 세션 포함)에서 업로드·다운로드가 되는지 확인한다 [미확인].
2. 구독 Reader 권한만으로 각 수집 명령(storage account list, container-rm list, nsg list, diagnostic-settings)이 성공하는지 확인한다 [미확인].
3. Resource Graph Explorer에서 공개 쿼리를 실행해 CSV 열 구성을 확인한다.
4. Entra 라이선스(P1/P2)와 역할을 확인하고, 포털의 "사용자 등록 세부 정보" CSV를 내려받을 수 있는지와 열 구성을 본다. 결과로 AZ-MFA-1 편입 여부를 정한다.
5. 판정 대조와 마스킹 골든 파일은 AWS와 같은 방식으로 한다.

### 17-2. 나중 범위 (우선순위순)
1. 일본어 정식판(v1.1, 원어민 검수)
2. 컷한 항목 복원(Before/After, 쌍둥이 비교)
3. AZ-MFA-1(편입되지 않았다면), Azure 앱 등록 시크릿(Graph)

7. 「설정탐정」 CTF(가짜 회사 재활용, 실제 점검과 헷갈리지 않게 표기)
8. 멀티 계정 보기(한 사람이 여러 계정 파일을 올림)
9. 교육용 공유 카드(결과 수치 없음, 클라이언트에서 만든 이미지, 위험이 있으면 비활성)
10. 규정 참고 대응표(FISC, 금융보안원, ISMS-P. 비인증, 판 번호·날짜 표기)
11. 서버 내부 sshd_config 10항목 점검기(PDF 1단계 실습 예)
12. 수집기 서명(cosign/minisign), 다음 점검일 .ics, 커스텀 도메인 정식화
13. 추가 룰(S3 암호화·버전 관리, 공개 스냅샷, Key Vault, 스토리지 네트워크 기본 허용 등)
